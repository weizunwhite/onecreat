## 全局规则（每一项都适用，修复前先读一遍）

1. **一项一个 commit**。commit message 格式：`fix(release): <本文档中该项标题>`。commit 后停下汇报，等确认再领下一项。
2. **改前必须先读代码验证问题仍存在**——本文档的行号是审查时快照，可能已漂移；以符号名/函数名定位为准。若发现问题已被顺手修掉或描述与代码不符，停下汇报，不要硬改。
3. **每项修完跑自查**：
   - 后端（root module）：`make vet && go test ./internal/... ./cmd/...`（涉及并发的加 `go test -race ./internal/agent/ ./internal/control/`）
   - desktop module：`cd desktop && go build ./... && go vet ./... && go test ./...`
   - 前端：`cd desktop/frontend && pnpm tsc --noEmit`
4. **后端修复尽量带回归测试**（去掉修复代码测试应当挂）。前端修复若无测试基建则在汇报里写清手测步骤。
5. **外科手术式改动**：只动该项列出的文件与逻辑，不重构、不改邻近代码、不改注释风格。中文注释。
6. **两个易错点**：本仓库有两个 Go module（root 和 desktop/），`go build ./...` 在根目录不含 desktop；`desktop/frontend/src/lib/bridge.ts` 是手工镜像 app.go 的，改 Go 导出签名必须同步 TS 接口 + mock + 调用点。
7. 修完如实汇报：动了哪些文件、有没有和描述不符的地方、有没有没把握的部分。

## 批次 A：内核 controller.go（3 项，同文件，顺序做避免冲突）

### A1【high】Summarize 后 checkpoint 边界未持久化失效 → resume 后 rewind 切错位 → API 400

- **位置**：`internal/control/controller.go` 的 `summarizeAt`（约 :1161），对照 `InvalidateCheckpoints`（约 :258-265）。
- **问题**：`SummarizeFrom` / `SummarizeUpTo`（"总结这一轮之后/为止"）会原地重写消息日志（`internal/agent/compact.go` 调 `session.Replace`），所有 turn 的消息下标位移。`summarizeAt` 只把内存里的 `cpBound` 清成空 map，**没有**像 compaction 路径那样调用 `c.cp.InvalidateBounds(turn)` 把"边界失效"持久化到磁盘（`.ckpt/bounds-min.txt`，`8db4059e` 加的机制）。
- **失败链路**：summarize → 关闭 → resume → `rebindCheckpoints` 从磁盘把陈旧 `MsgIndex` 填回 `cpBound` → 用户对旧 turn 做"仅对话" rewind → `Session.Truncate` 切在错误偏移，可能把 assistant(带 ToolCalls) 与 RoleTool 结果切开 → 悬空 tool_calls → 下次请求 OpenAI 兼容端点 400，且每次重试都 400（死循环感）。
- **修法**：`summarizeAt` 里在清内存 `cpBound` 的同时，走与 `InvalidateCheckpoints` 相同的持久化路径（调 `c.cp.InvalidateBounds(...)` / 记 `cpTurn` 阈值——直接复用/调用 `InvalidateCheckpoints` 最稳，注意锁的持有情况避免重入死锁）。
- **验收**：加回归测试：summarize → 模拟 resume（`rebindCheckpoints`）→ 断言陈旧边界不会回填（参照 `8db4059e` 为压缩路径写的既有测试，抄结构改触发方式）。去掉修复代码测试应挂。

### A2【medium】Checkpoints() 无锁读 c.cp 与 rebindCheckpoints 加锁写构成数据竞争

- **位置**：`internal/control/controller.go` `Checkpoints()`（约 :857-862）；写侧 `rebindCheckpoints`（:283-302，`c.mu` 下重新赋值 `c.cp`）。
- **问题**：`Checkpoints()` 裸读 `c.cp` 指针；而 `Resume` / `SetSessionPath` 会在 `c.mu` 下替换 `c.cp`，且这两条路径不走 `tryBeginExclusive`。桌面端"打开 rewind 抽屉"（Checkpoints）与"恢复历史会话"（ResumeSession→Resume）是不同 goroutine 的 Wails 调用，`-race` 可报。
- **修法**：`Checkpoints()` 改为 `c.mu.Lock()` 内捕获 `cp := c.cp` 后解锁再用——**照抄 `InvalidateCheckpoints`（:258-263）已有的写法**，那是本仓库自己的约定。
- **验收**：`go test -race ./internal/control/`。若容易构造，加一个并发调 `Checkpoints`+`Resume` 的 race 测试；不容易就说明改动为何充分。

### A3【medium】RemoveMCPServer 对项目级 [[plugins]] 声明的服务器只断连不落盘，下次启动静默复活

- **位置**：`internal/control/controller.go` `RemoveMCPServer`（约 :1487）。
- **问题**：`b205dcf5`（1b 方案）把持久化改成只写用户级 `LoadForEdit(UserConfigPath())`。若服务器只声明在**项目根 onecreat.toml 的 `[[plugins]]`** 里，用户级文件没有该条目，`RemovePlugin` 返回 `inConfig=false`，磁盘不改——UI 提示已移除，下次启动照常回来，无任何提示。这是 1b 引入的行为回退。
- **修法**（保持 1b 的原则——**绝不写全量合并快照**）：识别待删条目的 `Source`：
  - 来自用户级 → 现行逻辑不变；
  - 来自项目级 onecreat.toml → 对**该项目文件本身**做 `LoadForEdit(项目toml路径)+RemovePlugin+SaveTo`（单文件就地编辑，不引入合并快照问题）；
  - 来自 `.mcp.json` → 维持现状（该文件本就不写回 toml），但把"本次仅断开连接，配置来自 .mcp.json，需手动编辑该文件"的事实通过 notice 告知用户，不再静默。
- **验收**：测试三种 Source 的 remove 行为：用户级删条目、项目级删条目且**不产生全量快照**（断言项目 toml 里不会多出 provider/default_model 等无关键）、.mcp.json 走 notice。既有 1b 的"不创建项目级 toml"断言必须保持通过。

## 批次 B：provider openai.go（2 项，同文件）

### B1【high】网关模式上游错误体原样透传 UI，泄露真实模型名（双维度独立确认）

- **位置**：`internal/provider/openai/openai.go` 非鉴权 HTTP 错误路径（约 :217-220）与流中错误路径（约 :358-361）。现有的网关特判只盖了 401/403（:208-216）。
- **问题**：400/429/5xx 及 mid-stream error 把上游错误体逐字拼进 error，经 `TurnDone{Err}` → wire → 前端原样渲染。DeepSeek 的 context 超限 400 典型带 `for model deepseek-...` 字样——直接击穿"标准/高级/旗舰"档位抽象，违反 `config.ModelPrivacyPolicy` 铁律。
- **修法**：当网关模式（`keyEnv == "ONECREAT_GATEWAY_TOKEN"`，若已有 helper 判定则复用）时，**所有**错误路径不得包含上游 body/message 原文，改为映射成平台话术 + 状态码：
  - 400 → 「请求内容过长或不合法，请精简后重试(400)」
  - 429 → 「当前档位请求繁忙，请稍后重试(429)」
  - 5xx → 「服务暂时不可用，请稍后重试(5xx)」
  - 流中错误 → 「连接中断，请重试」
  - 非网关模式（用户自己的 key 直连）**保持现状**，直连用户需要原始错误排障。
- **注意**：不要把原始 body 写进任何日志文件（写盘同样泄露）；如需排障线索，只保留状态码。
- **验收**：加测试：网关模式下构造含 `deepseek` 字样的 400/429/500 响应体与流中错误，断言返回的 error 字符串不含上游 body 内容；非网关模式断言 body 仍透传。跑既有 `TestNewGatewayTierKeepsThinking` 等网关测试确认不回归。

### B2【medium】SSE 单行超 1MB 用 bufio.ErrTooLong 杀死整轮，已产出内容全丢且不重试

- **位置**：`internal/provider/openai/openai.go` `readStream` 的 `scanner.Buffer(make([]byte,0,64*1024), 1024*1024)`（约 :341）；`internal/provider/anthropic/anthropic.go` 同款（约 :314）。
- **问题**：网关/上游把大 reasoning 块或大 tool_call arguments 作为单个 `data:` 帧下发时（>1MB），Scan 直接 `bufio.ErrTooLong`，整轮报 `token too long` 失败，mid-stream 不重试（:162-165 注释），用户只能整轮重来。
- **修法**：两处上限提到 32MB（`scanner.Buffer(make([]byte,0,64*1024), 32*1024*1024)`）。不改成无界读——32MB 已远超任何合理单帧，同时保留对真正异常流的兜底。
- **验收**：加测试：构造一条 ~2MB 的合法 `data:` 行喂给 readStream，断言解析成功不报 ErrTooLong。两个 provider 都改、都测。

### C1【high】`reasonix mcp add/remove` 仍全量快照落项目级 toml，遮蔽用户配置（1b 漏修的第二入口）

- **位置**：`internal/cli/mcp.go`（约 :233 及 remove 对应处）。

## 批次 G：前端 useController.ts（3 项，同文件，**必须由同一个 agent 按顺序连续完成**，避免三次独立改动互相冲突）

### G1【high】un-send 撤回无 turn_done 的管理命令后 discardTurn 永久卡死，本标签后续消息全被吞

- **位置**：`desktop/frontend/src/lib/useController.ts`：send() 的 park 守卫（约 :627-632）、applyEvent 的 discardTurn 吞事件段（约 :194-197）、turn_done 冲刷（约 :538/:554-558）。后端事实：`event.TurnDone` 全仓唯一发射点是 `internal/control/controller.go` 约 :344 的 runGuarded；`#note`(QuickAdd)、`/tree` `/branch` `/switch` 及 managementNotice 类命令只发 Notice 永不发 TurnDone。
- **问题**：`0da04238` 的回归。用户发 `#note` 后在 Notice 回传前按 Esc → unsend 置 `discardTurn=true`；Notice 到达被吞，turn_done 永不来 → discardTurn 永久 true → 之后每条消息被 park 进 pendingResendRef 无人冲刷。消息框清空、无气泡、无报错，只能切标签自愈。
- **修法**（双保险，都做）：
  1. applyEvent：discardTurn 期间收到 `notice` 时**同样**清 discardTurn 并触发 pendingResendRef 冲刷（notice 是管理命令的终结事件，语义上等价 turn_done）；
  2. send() 守卫加运行态条件：仅当 `discardTurn && stateRef.current.running` 才 park；后端已 idle（running=false）时直接清 discardTurn 走 doSubmit（自愈兜底）。注意核对 unsend reducer 对 running 的处理，确保条件 2 在"真正在跑的 turn 被撤回"场景下仍保留原修复的防丢语义（即不会退回 0da04238 之前"静默丢弃重发"的老 bug）。
- **验收**：无前端测试基建则给出手测脚本：① 发 `#随便记一条` 立刻按 Esc → 再发普通消息 → 必须正常出气泡并得到回复；② 复验 0da04238 原场景：正常回合中 Esc 撤回 → 立刻重发 → 消息不丢、turn_done 后正常发出。`pnpm tsc --noEmit` 过。

### G2【high】切回运行中标签且回合在 History 拉取窗口内结束 → 助手回复渲染两次

- **位置**：`useController.ts` history 回填 reducer（约 :456，`ba4ad742` 改的"items 非空时把 historyItems 接在前面"分支）。
- **问题**：History() 返回完整消息日志（含刚完成落库的本回合 assistant 消息）；live 流已把同一条落成 a0 item → 前置回填后同一段回复出现两次，直到再切标签才自愈。修复前是丢历史（旧 bug），现在变重复（新 bug）。
- **修法**：回填时做重叠消除：history 与 live items 逐条比对（role+文本内容，从 history 尾部 vs live 头部找最大重叠段即可），把 live 中已存在于 history 的条目剔除（或反向——保留 live 版本剔除 history 重叠尾部，选实现更稳的一边并说明）。**目标不变式**：无论回合在 History() 解析之前还是之后结束，切回标签后每条消息恰好出现一次且历史完整。
- **验收**：手测脚本：标签 B 跑短回合，从 A 快速切回 B，反复 5 次（覆盖回合先于/晚于 History 解析两种时序）→ 历史在、无重复。tsc 过。

### G3【medium】切回标签时陈旧 Meta.running 覆盖已到达的 turn_done → spinner 永久转、输入框禁用

- **位置**：`useController.ts` `loadSessionData` 的 `restoreRunning`（约 :438）。
- **问题**：事件订阅在 reset 后同步注册，本回合 turn_done 可能先于 `app.Meta()` 的 promise 解析到达并清掉 running；随后 `restoreRunning(meta.running=true)` 把陈旧快照又置回 true。后端已 idle 不再发 turn_done → 前端永久 running 态。
- **修法**：加"自 reset 以来是否已观察到 turn_done"标记（reducer state 或 ref，与 G1/G2 改动统一考虑）：为 true 时 `restoreRunning` 不得把 running/turnActive 置回 true。或等价方案：restoreRunning 只在当前 state.running 仍为初始态时生效。选一种，说明为什么不引入新竞态。
- **验收**：手测：标签 B 回合临近结束时切回 B，反复多次 → spinner 不卡死、Composer 可输入。tsc 过。

## 批次 H：前端 OTAPanel（1 项）

### H1【medium】脚手架与发布两个独立项目名输入框，不一致则板子永久 404 静默不升级

- **位置**：`desktop/frontend/src/components/OTAPanel.tsx`：脚手架名 `scName`（约 :161）与发布名 `pubName`（约 :216）无联动。板端固件烤死 `FW_VERSION_URL = baseURL/sanitize(scName)/version.txt`；发布落到 `remoteDir/sanitize(pubName)/`。
- **问题**：老师两个框填的串 sanitize 后不同（`smart-bin` vs `smart_bin`）→ 板子永远 404，面板却提示"已发布，板子下次轮询自动升级"，无任何报错。
- **修法**（前端为主，最小化）：
  1. 脚手架生成成功后把 `scName` 同步为 `pubName` 的默认值（联动填充，仍可改）；
  2. 发布时若 `sanitize(pubName)` 与最近一次脚手架的 `sanitize(scName)` 不一致，发布按钮旁给醒目中文警告「项目名与新建时不一致，板子将拉取不到更新」，但不阻断（用户可能确实在发另一个项目）。
- **验收**：tsc 过 + 截图/手测描述两个场景（联动默认值、不一致警告）。sanitize 逻辑必须复用现有实现，不得前端重新实现一份。
