## 1. 文档目的与事实源规则

这份文档是 OneCreat 本轮架构重构的主执行计划，用于约束 ChatGPT、Claude Code、Codex 以及人工开发者后续的修改范围、顺序、测试和验收。

本轮重构的目标不是重写项目，也不是微服务化，而是在保持现有产品行为的前提下，逐步修正已经出现的架构边界问题，使 Desktop / CLI / Serve / ACP / 未来 dsh 能共享同一套清晰的运行时模型。

### 事实源优先级

执行架构重构任务时，按以下顺序理解仓库：

1. 当前分支真实源码与测试；
2. 本文件 `docs/架构重构执行总计划.md`；
3. 根目录 `AGENTS.md` 的工程约束与红线；
4. 其他历史文档与提交说明。

若 `AGENTS.md` 中存在本轮重构前的旧架构描述，例如“Desktop / Serve 分别维护 event wire 映射”，以当前源码和本计划为准；但 `AGENTS.md` 中关于双 Go module、Session 单写者、DeepSeek prefix cache、Checkpoint、硬件安全等工程约束仍必须遵守。

### 执行规则

- 每个 Plan 独立分支 / 独立 PR，除 Plan 00 当前已存在于 PR #2 外。
- 一个 Plan 只解决该 Plan 明确列出的架构问题。
- 不允许为了“顺手整理”扩展范围。
- 每个 Plan 必须先建立或确认回归测试，再修改实现。
- 每个 Plan 必须完成 diff 自审、跨平台 CI、已知风险说明后才能进入下一个 Plan。
- 不得因为 CI 基线已有红项而伪装为“本 PR 全绿”；必须区分新增回归与基线问题。

# 2. 当前架构概况

OneCreat 当前是 Go 重写后的多前端架构：

```text
CLI / TUI     HTTP / SSE     ACP     Wails / Web Desktop
     \            |           |             /
                  control.Controller
                         |
                     agent.Agent
                         |
                 Provider / Tool Registry
```

根模块负责 kernel、CLI、命令行工具；`desktop/` 是独立 Wails Go module。

当前已有一些值得保留的边界：

- `provider.Provider` 小接口 + registry；
- `tool.Tool` + per-run registry；
- `event.Sink` 作为内核向前端的单向事件边界；
- Session 的单写者模型与 Snapshot 约束；
- Checkpoint / rewind 的现有行为约束；
- DeepSeek prefix cache 的 append-only prompt 设计。

本轮重构不应无理由破坏这些边界。

# 4. 目标架构

目标不是引入更多层级，而是把 Transport、Application、Runtime Scope、Engine Adapter 明确分开。

```text
Transport
CLI / TUI / Wails / HTTP / SSE / ACP
                    |
                    v
Application
ChatService / SessionService / WorkspaceService / ApprovalService
AccountService / HardwareService / KnowledgeService / SettingsService
                    |
                    v
Runtime
ProcessRuntime
  └─ WorkspaceRuntime
       └─ SessionRuntime
            └─ TurnRuntime
                    |
                    v
Engine + Adapters
NativeEngine / DshEngine
Provider / Tool / MCP / Stores
```

## 四级资源作用域

### Process scope

建议承载：

- Account session；
- CredentialSource；
- HTTP clients；
- Updater；
- 全局不可变 catalog / factory。

### Workspace scope

建议承载：

- 显式 `Root`；
- workspace config；
- sandbox root；
- skills / memory index；
- CodeGraph；
- LSP；
- workspace MCP；
- workspace-level tool capability。

### Session scope

建议承载：

- Conversation；
- Session metadata；
- Checkpoint journal；
- Approval broker；
- session-specific MCP overlay；
- plan / coach / bypass 等会话状态。

### Turn scope

建议承载：

- `context.Context`；
- cancel handle；
- 当前模型请求；
- tool batch；
- usage；
- 临时 evidence / per-turn state。

# 5. 不可违反的重构红线

1. **不重写整个项目。**
2. **不微服务化。**
3. **一次只解决一个架构层。**
4. **不为了目录漂亮而大规模搬文件。**
5. **Workspace / Tab 边界完成前，不正式迁移 dsh。**
6. **不创建覆盖所有产品能力的巨型 Engine 接口。**
7. **不新增进程级隐藏全局状态。**
8. **先保持行为等价，再做功能增强。**
9. **不得破坏 Session 单写者 + Snapshot 约束。**
10. **不得把 per-turn runtime state 放入 DeepSeek cached system prefix。**
11. **任何会重排 Session message log 的改动必须继续正确处理 checkpoint boundary 失效。**
12. **安全 / Permission / Billing / Hardware honesty 行为不得在无明确计划时顺手改写。**

# 9. Plan 01 — 显式 WorkspaceContext

## 对应问题

A01。

## 目标

从：

```text
Workspace == process cwd
```

改为：

```go
type WorkspaceContext struct {
    Root string
}
```

Workspace root 必须显式传递，不再通过 `os.Chdir()` 表达运行时业务状态。

## 实施步骤

1. 全仓枚举 Workspace 语义下的 `os.Getwd()` / `os.Chdir()`；

# 11. Plan 03 — 四级 Runtime Scope

## 对应问题

A07。

## 目标

正式建立：

```text
ProcessRuntime
WorkspaceRuntime
SessionRuntime
TurnRuntime
```

## 每个 Scope 必须回答

- 谁创建？
- 谁持有？
- 谁 Close？
- 哪些资源共享？
- 哪些资源绝不能跨 Scope？

## 重点

本 Plan 先建立所有权模型和最小代码骨架，不要求同时把所有大文件搬目录。

## 验收

- 四级 runtime 的 ownership 清晰；
- Close 顺序有测试；
- 一个 Session 关闭不会误关共享 Workspace 资源；
- 一个 Turn cancel 不会关闭整个 Session。

## 状态

**已完成（2026-08-20）**，等待人工确认。分支 `refactor/runtime-scopes`，Draft PR #5
（base = `refactor/tab-manager`，栈式叠在 Plan 02 上）。

### 现状（本 Plan 的出发点，源码实证）

`boot.Build` 把 **所有** 资源串进同一个 `cleanup` 闭包：

```go
cleanup := pluginHost.Close                                    // MCP 子进程
cleanup = func() { prev(); codegraph.StopDaemon(daemonRoot) }  // CodeGraph 守护进程
cleanup = func() { prev(); lspMgr.Close() }                    // LSP servers
```

而它由 `Controller.Close()`——也就是**关闭一个会话**——触发。

于是只有一种生命周期，且是 Session 的。对**该共享**的资源这是错的：同一个项目开两个
标签，各自 `boot.Build` 一份运行时，关掉第一个标签就会停掉第二个标签正在用的
CodeGraph 守护进程。类型系统里没有任何东西说明「谁能共享、谁拥有、按什么顺序释放」，
每次都得重读 `boot.Build` 才能回答。

### 本 Plan 交付：`internal/runtime`

四级嵌套 scope，把上面那个答案写成代码：

```text
Process        一个进程一个
 └ Workspace   一个项目目录一个 —— 该项目下所有 session 共享
    └ Session  一次会话(一个桌面标签 / 一次 CLI run / 一个 ACP session)
       └ Turn  一个用户回合:模型请求 + 它的工具调用
```

**五个问题一次答清**（写进包文档）：

| | 谁创建 | 谁持有 | 谁 Close | 可共享？ |
|---|---|---|---|---|
| Process | 前端 | 前端 | 前端 | n/a |
| Workspace | `Process.OpenWorkspace` | Process | 最后一个 `Release`，或 Process 关闭 | **是**，按 root |
| Session | `Workspace.NewSession` | Workspace | `Session.Close`，或其 Workspace | 否 |
| Turn | `Session.BeginTurn` | Session | `Turn.End/Cancel`，或其 Session | 否 |

**绝不能跨界的**：注册在 Turn 上的资源不得活过该回合；Session 不得往它的 Workspace
scope 里注册。这条由 API 形状保证——`Defer` 是「你手里那个 scope」的方法，你只能把资源
挂到你真正持有的生命周期上，是编译期属性而不是口头约定。

**Close 顺序**：先关子 scope（父的资源在子 unwind 期间可能还需要），再按**注册的逆序**
释放自己的资源（后注册的可能依赖先注册的）。Close 幂等；某个 closer panic 不会中断
其余释放。

**Workspace 引用计数**：`OpenWorkspace` 同一 root 返回同一个 scope 并加一个 holder；
`Release` 到零才真正关闭并从注册表摘除（之后再 open 得到全新 scope，而不是复用尸体）。

### 特征测试（`internal/runtime/scope_test.go`）

- **Close 顺序**：`turn → session → workspace(逆序) → process(逆序)`；
- **Session 关闭不动 Workspace 资源**（本 Plan 的头号不变式，正对上面那个真实 bug）：
  关掉一个标签，workspace 的 codegraph/lsp 一个都不释放，兄弟 session 的 context 也不被取消；
- **Turn cancel 不关 Session**：只释放 turn 的资源，session 还能开下一个 turn；
- 反方向的包含关系：**Session 关闭必须结束它正在跑的 Turn**；
- 一个 session 同时只有一个 turn（开新的会先结束旧的，避免漏掉上一个 turn 的 context）；
- Workspace 按 root 共享 / 不同 root 不共享 / 最后一个 Release 才关 / **过量 Release 不得报告第二次关闭**；
- Close 幂等 + panic 安全；关闭后 `Defer` 立即释放（不泄漏）；
- 父 scope 关闭中再开子 scope，子 scope 立刻是关闭态（不会活过父）；
- context 只向下取消，绝不向上；
- 8 goroutine × 40 轮并发生命周期，`-race` 干净，且 open/release 平衡后无残留。

> 写测试过程中就抓到一个真 bug:`Release()` 在 holders 已经为 0 时仍报告
> 「我关闭了它」。调用方据此去拆资源，就会拆掉之后 `OpenWorkspace` 已经交给别人的
> 那份。已修:只有真正减到零的那次才报 true。

### 验证结果

PR #5 head `972f954`（CI run `32403239151`）——**5/5 全绿**：
Ubuntu / macOS / Windows / Desktop / Race。
另本地 `go test -race ./internal/runtime/`、`GOOS=windows go vet ./...` 通过。

### 本 Plan 明确**未**做（按计划文档「先建立所有权模型和最小代码骨架」）

`internal/runtime` 目前**尚未接线**到 `boot.Build` / `Controller` / desktop —— 这是
**Plan 04**（统一 RuntimeFactory，单一装配入口）和 **Plan 05**（MCP / CodeGraph / LSP /

```go
func (w *WorkspaceRuntime) NewSession(...) (*SessionRuntime, error)
```

Transport 不应自己知道如何拼：

- Provider；
- Tool Registry；
- Permission；
- Planner；
- MCP；
- Memory；
- Gateway policy。

## 验收

ACP 不再保留一整套独立 `provider + tools + agent + controller` assembly。

## 状态

**已完成（2026-08-20）**，等待人工确认。分支 `refactor/runtime-factory`，Draft PR #6
（base = `refactor/runtime-scopes`，栈式叠在 Plan 03 上）。

### 现状与证据

`boot.Build` 早已是 Desktop / CLI / Serve 的唯一装配入口。**唯一绕过它的是 ACP**：
`internal/cli/acp.go` 手工拼了一整套 provider → tool registry → MCP host →
permission → task tool → executor → planner coordinator → controller，注释里写着
「mirror boot.Build」「与 boot.Build 的 `!gatewayActive` 门禁一致(F1)」——**每一条被
手抄的规则都是计费 / IP 敏感的**（网关改写、模型隐私提示词、网关下关掉 planner）。
两份靠人手保持一致，就是漂移的定义。

### 改动

`internal/cli/acp.go` **206 → 121 行**，`NewSession` 变成一次 `boot.Build` 调用。
它不再 import `agent` / `permission` / `plugin` / `tool` / `tool/builtin` /
`command` / `event` —— 那串「imported and not used」正是验收证据。

`boot.Options` 增加两个、且只有两个 ACP 真正需要的输入：

- `ExtraPlugins []plugin.Spec` —— 客户端在 `session/new` 里声明的 MCP 服务器，
  与配置里的一起 eager 启动（宿主点名的服务器，第一轮就得有）；
- `HostProvidesCodeIntel bool` —— 抑制两个会自己拉起长驻子进程的 workspace 服务
  （CodeGraph 守护进程、LSP manager）。编辑器宿主本来就跑着自己的 language server
  和索引，在 agent 里再起一套是纯浪费。**其余一切（memory、skills、hooks、jobs、
  提示词策略）按同一条路径装配。**

`control.Controller` 增加只读的 `ToolNames()`：让「装配根到底把哪些可选服务接进了
这个 session」可观测。此前 `boot_test.go` 里就留着一句

规则，不少任何保护），但这确实是**本 PR 唯一改变的既有行为**，`acp_test.go` 里已把

### 防漂移测试（`internal/cli/acp_assembly_test.go`）

# 13. Plan 05 — 资源生命周期收口

## 对应问题

A06、A07。

## 重点资源

逐个明确：

- CodeGraph；
- LSP；
- MCP；
- Jobs；
- background goroutines；
- Skill / Memory indexes。

## 示例期望

```text
Workspace A
 ├─ Tab 1
 ├─ Tab 2
 └─ shared CodeGraph
```

关闭 Tab 1 不应杀掉 Tab 2 正在使用的 Workspace CodeGraph；只有 WorkspaceRuntime Close 才释放它。

## 验收

- 资源按作用域只创建一次；
- 引用 / ownership 可解释；
- Close 无泄漏、无 double-close；
- 有生命周期回归测试。

## 状态

**已完成（2026-08-20）**，等待人工确认。分支 `refactor/resource-lifecycle`，Draft PR #7
（base = `refactor/runtime-factory`，栈式叠在 Plan 04 上）。

### 现状与证据

`internal/boot/boot.go` 把**所有**资源串在同一条生命周期上——session 的：

```go
cleanup := pluginHost.Close                                    // MCP 子进程
cleanup = func() { prev(); codegraph.StopDaemon(daemonRoot) }  // CodeGraph 守护进程
cleanup = func() { prev(); lspMgr.Close() }                    // LSP 服务器
```

这条链由 `Controller.Close()` 执行，也就是**关一个会话**时。而 CodeGraph 守护进程在
仓库里自己就写着「**按工作区共享**」（`internal/codegraph/codegraph.go`
`StopDaemon` 的注释），LSP 服务器同理——于是同一个项目开两个标签时，关掉其中一个会
把另一个正在用的语言服务器和符号守护进程一起停掉。这正是本 Plan「示例期望」那张图。

### 改动

**`internal/boot/factory.go`（新增）**——`Factory` 持有进程级 + 工作区级那一半运行时：

- `NewFactory(ctx)` 开一个 `runtime.Process`（Plan 03 的作用域模型，至此不再是摆设）；
- `OpenWorkspace(ws, WorkspaceSpec)` 按 `ws.Root()` 引用计数地拿一份工作区共享服务，
  首次打开时启动它们，并把 teardown 注册在 **workspace scope** 上；
- `Hold(ws)` 是不带服务的纯生命周期引用（见下）；
- `WorkspaceHandle.Release()` 用 `sync.Once` 保证「恰好释放一次」，最后一个持有者
  走掉时工作区才关闭。

`Factory` **显式传递、绝不全局**：`boot.Options.Factory` 为 nil 时该会话自带一个私有
工厂并随它关闭——即 Plan 05 之前的行为，也正是「一个进程一个工作区」的 CLI /
headless / ACP 想要的。这条是本轮红线「不新增进程级隐藏全局状态」的直接落实。

**`internal/boot/boot.go`**——三级归位：

| 资源 | 归属 | 释放时机 |
|---|---|---|
| LSP manager | workspace | 最后一个持有者释放工作区 |
| CodeGraph 守护进程（`StopDaemon`） | workspace | 同上 |
| MCP plugin host | session | `Controller.Close()` |
| jobs / background goroutines | session | 同上 |
| skill / memory index | 每次 build 的快照，不是资源 | —— |

`Build` 现在开一个 `runtime.Session` 挂在工作区作用域下，MCP host 在**创建它的那一行**
就 `sess.Defer("mcp-host", …)`（用闭包，因为 eager 那一档会换掉 host 变量）——所有权
写在产生所有权的地方，任何错误返回都漏不掉。

### 为什么 `workspaceServices` 里没有别的东西

写在类型注释里，这里摘要：MCP host 是 session 的（`/mcp add` 热加进的是**这个**会话
的 host，且会话可能带客户端 overlay）；jobs 是 session 的（任务属于开它的那段对话）；
skill / memory index 是每次 build 的快照、会折进缓存稳定的 system prompt，按工作区
缓存反而会让「改完 AGENTS.md 后新开的会话仍读到旧文本」——拿一个真实的正确性换一点
可忽略的开销。

**CodeGraph 二进制路径也有意不缓存**：`auto_install` 是后台下载的，提示语承诺「下个
会话可用」；一旦按工作区缓存解析结果，那就变成「这个项目所有标签都关掉之后才可用」。
所以工作区上只挂 teardown（`StopDaemon` 找不到 pidfile 时是 no-op），解析仍每会话做。

### `HostProvidesCodeIntel` 下沉到 `WorkspaceSpec`

编辑器宿主自带 language server 和索引，这类会话**既不该起** CodeGraph 守护进程，
**也不该停**一个它没起过的——守护进程是跨进程按工作区共享的，杀掉会打到同机开着同
一项目的 desktop OneCreat。Plan 04 只用这个标志抑制「起」，本 Plan 把它下沉到工厂，
连「停」一并抑制。

### `Factory.Hold`：跨重建持住工作区

Desktop 的三条重建路径（`SetModel` / `rebuildTabByID` / 设置变更 `rebuild`）都是
**先 Close 旧 controller、再 Build 新的**。两个会话要的是同一个项目，但中间那一小段
时间没有任何人持有它——引用计数 1→0→1，工作区关掉再立刻重开，语言服务器和守护进程
白白冷启动一次。`App.holdWorkspace` 在这三处跨重建持一份显式引用，把意图写清楚：
**我在换这个项目上的会话，项目本身别关。**

### 生命周期回归测试

`internal/boot/factory_test.go`：

- 同项目两个 `Build` 只开**一个**工作区作用域；关掉第一个后工作区仍在（本 Plan 的
  正题）；关掉第二个才释放；
- `Controller.Close()` 重复调用不得把工作区从还活着的会话手里抢走（`sync.Once`）；
- 两次 `OpenWorkspace` 拿到**同一份**服务；工作区关闭后重开是全新的一份；
- `Hold` 期间工作区不关，重建后的会话拿到的仍是**同一份**服务（没被停掉重启）；
- `Factory.Close()` 之后没有开着的工作区，迟到的 `Release` 无害；
- session 作用域：两个 controller = 该工作区下两个 session，逐个关闭 2→1→0，而
  工作区由持有者决定生死。

`desktop/lifecycle_test.go`：

- `holdWorkspace` 对裸 `&App{}` / nil receiver 安全；持有期间项目保持打开；
- AST 守卫：desktop 里**每一处** `boot.Build` 都必须传 `Factory`（漏一处，那个标签
  就独占一份私有服务，且完全无声）；
- AST 守卫：三条重建路径必须调用 `holdWorkspace`。

反向验证（临时改坏再跑）确认这些测试**真的会红**，不是摆设。

### 验证结果

PR #7 head `a464e2b`(CI run `32407268249`)——**5/5 全绿**:
Ubuntu / macOS / Windows / Desktop / Race。
本地另跑 `GOOS=windows go vet ./...`、`GOOS=darwin go vet ./...`、
`go test -race ./internal/agent/ ./internal/control/ ./internal/boot/ ./internal/runtime/` 全部通过。

### 遗留

- `runtime.Turn` 仍未接线——回合级资源（在途工具调用的取消）归 Plan 07/08 拆
  Controller / Agent 时处理，本 Plan 不扩大范围；
- `SwitchWorkspace` 不需要 `Hold`：它换的是**另一个**根，旧根由旧 controller 关闭时
  释放，且新 controller 先 Build 后 Close 旧的。

`app.go` **3766 → 710 行**。每个服务自己持有状态与锁,依赖【用函数注入】而不是回指

`bridge.ts` 里那份 **120 来个方法的 `AppBindings` 接口是手抄的**,而守住它的

- **单一显式 API surface**:`rpcPublicMethods` 仍是显式 opt-in —— 给 `*App` 加导出方法

### 现状与证据

### 改动:六个服务 + 一个兼容 facade

`controller.go` **1923 → 756 行**。按计划推荐的顺序拆(ApprovalBroker → CheckpointService
→ SessionService → …),每个服务各带自己的锁:

| 服务 | 文件 | 自己的状态 |
|---|---|---|
| `approvalBroker` | `approval.go` | 审批/ask 的待应答表、会话授权、YOLO/bypass、批准计划窗口 |

| `memoryService` | `memory.go` | 记忆快照 + 「随下一轮注入」的待发注记 |

**Controller 现在一把锁都没有**(`startedOnce` 改成 `atomic.Bool` 的 CompareAndSwap,

命令路由那半按职责分了文件(纯搬家):`router.go`(`Submit`——认出该走哪条既有原语,
自己不实现任何领域动作)、`plan_seed.go`、`branches.go`。

### 三处值得单独记的决定

- **`sessionStore` 有意不拥有消息日志。** 日志是 `agent.Session`,单写者设计(只有
  run-loop goroutine 追加)。这个类型拥有的是**文件**,需要一致副本时经 `Snapshot()` 读。
- **`memoryService` 把快照和待发注记绑在一起,理由是前缀缓存。** 快照进的是缓存稳定的

  turn-tail 注记,由 Compose 在下一轮取走 —— 立刻生效、只花一轮的 token、下个会话免费
  折进前缀。
- **换会话路径是两步,由 Controller 编排。** `sessionStore` 换文件、`checkpointService`
  重绑,两个服务互不知道对方。

nil 时懒创建 —— 两个指针会分叉,`Host()` 读到的和实际连着服务器的不是同一个。host 现在
只有一份。

# 17. Plan 09 — Account / CredentialSource

## 对应问题

A12。

## 当前问题

当前流程把：

- `ONECREAT_GATEWAY_URL`
- `ONECREAT_GATEWAY_TOKEN`
- `ONECREAT_TIER`

作为运行时依赖注入 / 状态总线。

## 目标

```go
type CredentialSource interface {
    Token(context.Context) (string, error)
}
```

并建立显式 Gateway / Account runtime。

## 原则

- Token refresh 更新 CredentialSource；
- Provider 下一次请求读取新 token；
- 不需要靠 `os.Setenv()` 通知其他组件；
- 对 dsh 子进程可以在 Adapter 启动边界临时投影为 env，但 env 只是传输格式，不是应用状态源。

## 验收

业务运行时不再依赖进程环境变量来传播账号状态。

## 状态

**已完成(2026-08-20)**,等待人工确认。分支 `refactor/account-credentials`,Draft PR #11
(base = `refactor/agent-policy-boundary`,栈式叠在 Plan 08 上)。

### 现状与证据

桌面端 `os.Setenv` 写这三个变量,`boot` / `provider` / 斜杠路由各自 `os.Getenv` 读回去;
token 续期靠「改一个全局」来通知所有已建好的会话。

这不是风格问题:

- **不可见耦合** —— 调用签名里没有任何东西说明 provider 依赖账号状态,所以拦不住第二个
  组件去写它;
- **进程级** —— 两个会话永远不可能持不同账号;
- **测试污染** —— 测试里设一次就泄漏到同一二进制内的其它测试。

### 改动:`internal/account`

```go
type CredentialSource interface { Token(ctx context.Context) (string, error) }
```

`Gateway` 是显式的账号运行时(URL / token / 档位,自带读写锁)。谁拥有账号(桌面 `App`)
就持有它并在登录 / 续期 / 切档 / 登出时更新;谁需要 token 就拿一个 `CredentialSource`。
**provider 每次请求都问一次**,所以续期后的下一次请求自动用新 token —— 与从前一样无需
重建,但不再经由 `os.Setenv`。

`boot.Options.Gateway` / `control.Options.Gateway` 把它显式传下去;桌面所有 `boot.Build`
调用点(含 `tabRuntimeService` 的四条重建路径)传的都是**同一个对象**。

### env 剩下的两个合法用途

都是**传输**,不是状态源:

- `account.FromEnv()` —— 进程带着变量启动时导入**一次**(旧版脚本 / 打包器 / 编辑器拉起的
  ACP 子进程)。之后对象就是唯一真源,再改 env 无效;
- `Gateway.Env()` —— 把会话投影给只能这么配置的子进程,为计划里写明的 dsh 适配器边界预留。

### 顺带修掉一处「按字符串推断安全行为」

provider 是否处于网关模式,过去靠 `keyEnv == "ONECREAT_GATEWAY_TOKEN"` 的**字面量匹配**
判断 —— 而这个判断决定「上游错误 body 是否可以原样外抛」(400 的 `for model deepseek-…`
会击穿档位抽象)。现在是构造时的显式 `Gateway` 标志,与 credentials 在同一个分支里一起设。

### 验证结果

PR #11 head `32d599b`(CI run `32417346801`)——**5/5 全绿**:
Ubuntu / macOS / Windows / Desktop / Race。
本地另跑 `GOOS=windows go vet ./...`、`GOOS=darwin go vet ./...`、
`go test -race ./internal/account/ ./internal/control/ ./internal/boot/`、
desktop `go test -tags web ./...`,全部通过。

### 遗留

- `ONECREAT_ACCOUNT_MODE`(`platformAccountEnabled`)仍读 env —— 它是**部署模式**开关,
  进程启动即固定、运行期不变,不属于「传播账号状态」,故有意保留。

### 防漂移测试

`internal/account/boundary_test.go` 扫描**全仓非测试源码**:任何包(本包除外)出现
`os.Getenv/Setenv/Unsetenv` 这三个变量即报错。反向验证过会红。

`internal/account/account_test.go` 钉住语义:续期能到达**已建好的** `CredentialSource`、
签出即完全无账号(含 nil 接收者)、`FromEnv` 只导入一次(之后改 env 无效)、`Env()` 投影、
并发读写(`-race`)。

# 18. Plan 10 — Event Protocol V2 + Reliable SSE

## 对应问题

A11。

## Event 建议字段

```text
SchemaVersion
EventID
Sequence
SessionID
TabID
Timestamp
Kind
Payload
```

## QoS 分类

### Ephemeral，可合并 / 可丢

- text delta；
- reasoning delta；
- tool progress。

### Durable，不得静默丢

- approval request；
- ask request；
- message；
- tool result；
- turn done；
- session changed。

## SSE 要求

慢消费者不能简单 `default: drop` 所有事件。

允许方案：

- delta coalesce；
- durable queue；
- backpressure；
- disconnect + sequence replay；
- snapshot + replay。

## 验收

慢客户端不能因为 buffer 满而静默错过 approval / turn_done 等关键状态。

## 状态

**已完成(2026-08-20)**,等待人工确认。分支 `refactor/event-protocol-v2`,Draft PR #12
(base = `refactor/account-credentials`,栈式叠在 Plan 09 上)。

### 现状与证据

两条 SSE 扇出都是「缓冲满就丢这一帧」,而且丢的是**任意**一帧:

```go
internal/serve/broadcaster.go:38   default: // subscriber is behind; drop this frame for it
desktop/eventstream.go             default: // 慢客户端:丢这一帧,绝不阻塞 agent goroutine
```

浏览器卡一秒丢几个 token 增量无所谓;丢一个 `approval_request`,agent 就**永远阻塞**在
一个没人看得见的提示上;丢一个 `turn_done`,UI 就永远转圈。而且丢得**无声** —— 两端事后
都无法知道发生过。

### 改动:三层

**1. QoS 分级(`internal/event`)** —— `Kind.Delivery()` / `Kind.Durable()`。

只有三种是 Ephemeral:`reasoning` / `text` / `tool_progress`。它们的共同点不是「不重要」,
而是**后一条会取代它**(下一个增量,或收尾的 `message` / `tool_result`)。其余一律 Durable,
而且**默认 Durable**:新加的 kind 在有人证明它可丢之前都算状态帧 —— 漏分类要往安全的方向漏。

**2. Event Protocol V2 信封(`internal/eventwire`)** —— 计划里列的字段逐条落地:
`schemaVersion` / `eventId` / `sequence` / `sessionId` / `tabId` / `timestamp`,外加 `durable`
(把服务端的 QoS 判断也告诉客户端,这样它能判断「我察觉到的这个洞里可能是什么」)。

`sequence` 逐条递增且无洞 —— 这是客户端**能够察觉**丢帧的前提。信封由 `Stamper` 盖,不由
`Encode` 盖:序号属于一条**流**,不属于一个事件。`Encode` 仍只产出 payload,所以既有的
payload 契约测试原样通过 —— 这本身就是「payload 没有漂移」的证据。

**3. 可靠交付(`internal/eventstream`)** —— 一份实现,两个传输共用:

- 增量在积压时丢(与从前一样,这对渲染增量是对的);
- 状态帧**只排队,不丢**;
- 完全不消费状态帧的客户端(队列打满硬上限)被**断开**并收到 `stream_reset`,重连后重新
  对齐 —— 计划允许的「disconnect + 重新对齐」方案。**静默继续是本 Plan 唯一排除的选项。**
- `Publish` 永不阻塞:它跑在 agent 的运行循环 goroutine 上,卡住它等于卡住整个会话。

### 防漂移测试

- 两个传输各一条端到端验收:增量洪水之后 `approval_request` / `turn_done` **必须仍在**;
- 超过 durable 硬上限要**判死**而不是悄悄裁剪;
- `Publish` 不阻塞(真阻塞就是死锁,`go test` 超时打全栈比断言更好定位)、顺序保持、
  扇出互不影响、`-race` 并发;
- `sequence` 无洞、并发盖章不重号、`Encode` 不碰信封;
- 分级本身:三种增量必须 Ephemeral,计划点名的六种必须 Durable,**未分类的 kind 必须
  默认 Durable**。

反向验证:把 `ApprovalRequest` 标成 Ephemeral,分级测试与两条传输验收测试同时变红。

### 验证结果

PR #12 head `135aa81`(CI run `32419068521`)——**5/5 全绿**:
Ubuntu / macOS / Windows / Desktop / Race。

# 19. Plan 11 — Session / Persistence 统一所有权

## 对应问题

A15。

## 原则

OneCreat 统一管理：

- session identity；
- workspace；
- engine type；
- title；
- timestamps；
- metadata；
- engine store reference。

底层 Engine 可以管理自己的原始 transcript。

禁止：

```text
Go 保存一份 transcript
+
dsh 再保存一份 transcript
+
两边长期双向同步
```

一个 Session 必须有一个明确的对话真源。

## 验收

Native / ACP / dsh 的 session identity 与 storage ownership 可解释、可恢复、无双写真源。

## 状态

**已完成(2026-08-20)**,等待人工确认。分支 `refactor/session-persistence`,Draft PR #13
(base = `refactor/event-protocol-v2`,栈式叠在 Plan 10 上)。

### 现状与证据

会话的「身份」就是它的 transcript 文件名(`<时间戳>-<模型>.jsonl`),元数据散在**四份并列
的侧车文件**里 —— `.titles.json` / `.display.json` / `.cwds.json` / `.kinds.json` —— 每份一套
load/save 样板、都按文件名索引、**都只有桌面端会写**。

后果三条,都能在改动前的代码里指出来:

- `deleteSessionFile` 删一个会话要做**四次**读-改-写,漏一个就留下孤儿元数据;
- CLI / ACP 起的会话**完全没有元数据** —— 没有标题、不知道属于哪个项目;
- 没有任何地方记录「这份 transcript 是哪个引擎产生的」。所以第二个引擎(dsh)只能靠
  「再存一份 + 长期双向同步」接进来 —— 正是本 Plan 明令禁止的形状。

### 改动:`internal/session`

一个 `Record` 拥有身份 / 引擎 / **store 引用** / 项目 / 标题 / 类型 / 时间戳 / display 映射;
一个 `Registry` 用单个 `.sessions.json` 索引管理它们。

**`Store` 是引擎对 transcript 的引用,注册表从不解析它。** 对话本身只有一个真源,那就是
引擎的 —— 这正是计划里那句「底层 Engine 可以管理自己的原始 transcript」的落地形式:

# 19.7 Plan 11 收尾:一个在最终一致性核对中抓到的真 bug(已修)

Plan 12 完成后按最终报告的要求做「docs / AGENTS.md 与代码是否一致」的逐条核对,核到
「Plan 11:`session.Open` 唯一调用点」这一条时发现:**全仓库有两处**,而且都合法 ——
`desktop/sessions_service.go`(历史面板)与 `internal/control/session_store.go`(每个
会话自己注册身份)。Plan 11 当时立的守卫是 desktop 包内唯一,它没说错,只是没覆盖到
跨包的那一处。

## 这不是竞态,是必然丢更新

`Registry.load()` 上原有一个 `loaded` latch:读一次之后**永不重读**;而 `save()` 每次
把**整份**内存快照写回。于是在 desktop 进程里:

1. 历史面板刷新 → UI 侧 registry 读到 N 条并缓存;
2. 新开一个标签 → 该标签 Controller 的 registry 读到 N 条,`Ensure` 后写回 N+1 条;
3. 用户改任意一个会话的标题 → UI 侧内存里**还是**那 N 条,写回 → 第 2 步那条**没了**。

后果正是 Plan 11 要消除的东西:会话丢掉身份与 workspace,下次再 `Ensure` 会拿到一个新
ID(而 `Workspace` 是 write-once 的,重建时只能重新推断)。转录文本不受影响 —— 索引从不
碰它。

严重度:**中**。触发条件是「开新标签 + 改标题」,都是日常操作。

## 修法(最小):每次操作前重读

去掉 `loaded` latch,`load()` 改名 `sync()`,在每个操作前重读索引。代价是每次多一次几 KB
的 `ReadFile`;这些操作全是用户触发的低频动作(新建会话、改标题、刷新历史面板),拿这点
开销换掉一整类「会话记录莫名消失」是划算的。

回归测试 `TestSecondOwnerDoesNotClobberTheFirst` 直接照上面三步复现,**反向验证过**:把
latch 加回去立刻变红。

写测试时还顺带撞到一件事,记在这里免得后来人重蹈:`SetTitle` 的第一个参数是 **store
引用**,不是 ID;传错时它静默返回 nil。第一版测试就是这么写错的,一度让我以为
`SetTitle` 根本不落盘。

## 残留限制(如实记下,不在本轮修)

两个 owner 的「读—改—写」仍可能交错,各自的 `mu` 管不到对方。窗口是微秒级,且要求两个
低频用户动作恰好同时发生。彻底消除有两条路:

1. 索引文件级的锁(跨进程也管用,但要处理陈旧锁);
2. **让整个进程共用一个 `Registry`** —— 更对的形状,而且与 Plan 05 的所有权模型一致:
   Registry 是进程级服务,应当由 `boot.Factory` 持有,再传给 `control.Options` 与
   desktop 的 `sessionService`。之所以没在这里做,是它要动 `boot.Factory`、
   `control.Options` 与 Plan 06 的服务装配三处,属于另一件事;而且当前 CI 不可用,
   在拿不到跨平台验证的情况下扩大改动面不划算。

建议:作为 Plan 11 的后续项单独立项(或在合并前一并处理),优先级中。

# 20. Plan 12 — 最小 TurnEngine abstraction + dsh

## 对应问题

A14。

## 禁止的接口

不得创建本质上复制 Controller 的巨大接口，例如：

```go
interface Engine {
    Submit(...)
    Cancel(...)
    Approve(...)
    History(...)
    Resume(...)
    Fork(...)
    Rewind(...)
    Plan(...)
    // ... dozens more
}
```

## 推荐最小边界

```go
type TurnEngine interface {
    Start(ctx context.Context, req TurnRequest, sink EventSink) (TurnHandle, error)
}

type TurnHandle interface {
    Cancel() error
}
```

其他能力使用 capability interface 或 capability matrix：

```text
Streaming
Approval
Resume
Fork
```

## 最终结构

```text
OneCreat Application Policies
├─ Memory
├─ Evidence
├─ Permission
├─ Billing
└─ Checkpoint
        |
        v
    TurnEngine
    /       \
Native      dsh
```

## 验收

dsh 是 Engine Adapter，不成为第二套 OneCreat application core。

## 执行记录(branch `refactor/engine-dsh-adapter`)

### 落地形状

```
internal/engine/           TurnEngine / TurnHandle / Capability —— 边界本身,不依赖任何引擎
├─ native/                 包 agent.Runner(Agent 或 Coordinator)
└─ dsh/                    在既有 sidecar 驱动之上加 Adapter
```

`control.Controller` 上原来的 `runner agent.Runner` 换成唯一的 `engine engine.TurnEngine`,
三处 `runner.Run(...)` 收敛成一个 `runEngineTurn`。**这是 Controller 与「谁来跑」之间仅有的
接触点** —— 记忆 / 证据 / 权限 / 计费 / 检查点全部留在它之上,对两种引擎一视同仁。

`boot.selectEngine`(`internal/boot/engine.go`)按 `engine = "native"|"dsh"` 装配。

### 三处与计划文档的偏差(都有源码理由,已如实记录)

1. **`TurnHandle` 多一个 `Wait`。** 文档草图只有 `Cancel`,没有任何「跑完了」的信号;
   而既有的 `agent.Runner.Run` 是同步的,Controller 要在它返回之后才收尾(Stop hook、
   plan mode 审批门、落盘)。没有完成信号就无法表达既有语义。只补这一个方法,守卫把
   `TurnHandle` 钉死在两个方法。
2. **`Start` 不收 sink 参数。** 文档草图是 `Start(ctx, req, sink)`。但 sink 是**会话级**
   的,不是回合级:两种引擎都在构造时就绑定了它。每轮再传一次,等于给「这个会话的事件
   去哪儿」留下第二个答案 —— 正是规则 6 禁止的形态。
3. **`control.Options` 同时保留 `Engine` 与 `Runner`。** `Runner` 是「用内置内核」的简写,
   既有的二十多个调用方与测试都靠它;`New` 在构造时立刻把两者收敛成唯一的
   `Controller.engine`(`Engine` 优先),构造完不存在第二个真源。有用例锁住这条。

### 唯一一处有意的行为变化

内置引擎的一轮现在跑在适配器起的 goroutine 上,而不是调用方那条。这触及内核红线
「Session 单写者 + 同 goroutine 免锁读」,因此 `Wait` 的契约写死为:**绝不在运行
goroutine 真正退出之前返回**(`TestWaitNeverReturnsWhileTheRunnerIsStillRunning`)。
提前一步返回,就是 Controller 在 agent 还在写 `Session` 时去读它。全量 `-race` 干净,
`internal/control` 与两个适配器包都开着 goleak。

### 顺手消掉的一个不诚实配置项

`engine = "dsh"` 在此之前**不生效**:`cfg.Engine` 除了被渲染进 TOML 没有任何消费者,
用户写了它也只会静默跑 native。现在它真的选引擎,而且配错一律在**装配期**失败
(未知引擎名、缺 `bin_path`、sidecar 拉不起来),绝不静默回退 —— 让人以为自己在用
dsh 比启动失败糟得多。

### 能力矩阵(说实话,而不是假装都支持)

| | streaming | approval | resume | fork |
|---|---|---|---|---|
| native | ✅ | ✅ | ✅ | ✅ |
| dsh | ✅ | ❌ | ❌ | ❌ |

dsh 的三个 ❌ 都不是保守起见,是真的没有:它的工具跑在自己的进程里,OneCreat 的权限门
够不着;会话日志在它那边,照着本地日志 rewind / branch 只会让两边悄悄对不上。未声明
`Capable` 的引擎一律按「什么都不支持」处理 —— 失败方向朝安全。

### 防漂移守卫(全部反向验证过会红)

| 守卫 | 反向验证 |
| --- | --- |
| `TurnEngine` 只能有 `Start` | 加 `Rewind` 并补齐所有实现 → 红 |

| `TurnHandle` 只能有 `Cancel`/`Wait` | — |

直至 `go test` 超时。仍然是红,但不是我原本设想的那种红,记在这里免得后来人按错误的

### 已知限制(不在本 Plan 解决)

- dsh 的 JSON-RPC 没有 mid-turn 取消,取消降级为关掉 sidecar 进程 —— spike 报告里就
  写明的取舍,本 Plan 没有改变它,只是把它如实暴露成 `Cancel` 的语义。

## Wave B(进行中)—— AR-R09 已完成(branch `fix/session-registry-cas`)

复核指出:`Registry.mu` 只管得住自己那一个实例,而一个进程里必然有多个 Registry
(desktop 的 sessionService 一个、每个标签的 sessionStore 又各有一个),Desktop + CLI
更是两个进程。「读整份 → 改一条 → 写回整份」在两个 owner 之间交错,后写的那个会把前一个
的改动整条抹掉。原来的注释把这个窗口如实记着,但没有关掉;测试也只覆盖了同一个实例上的
多个 goroutine —— 那由 `mu` 挡住了,测不到真正的问题。

**这不是理论风险。** 反向验证(去掉锁)时,两个 owner 各写 40 条,最后磁盘上只剩 **44/80**
—— 一半的会话记录当场消失。

修法:索引目录下一个 lockfile,`O_CREATE|O_EXCL` 在所有平台上都原子,不需要 cgo,也不依赖
平台各异的 flock。每一次「读—改—写」整体在锁内进行(`ensureLocked`/`updateLocked`/
`forgetLocked`)。两处刻意的取舍都写在 `internal/session/lock.go` 的文件头:

- **陈旧锁会被接管**(持锁进程被 kill -9 后锁文件会留下;不接管的话,一次崩溃会让这台机器上
  的会话元数据永久只读);
- **拿不到锁时放行并记 warn**,而不是让用户的一次改名失败 —— 那比它要防的问题更烦人。

测试按复核的要求造**两个独立 Registry 实例**:并发新建(80 条一条不少)、并发改同一条记录
(标题与 display 都不被对方抹掉)、陈旧锁接管、新鲜锁必须等待且释放后删除、锁文件不得被
当成会话记录。

**补做:真正的跨进程用例。** 复核原话是「至少一个测试使用两个进程或可控 barrier 复现
交错」,我第一版只做到「两个 Registry 实例」—— 那是同一个进程。这不是吹毛求疵:进程内的
两个实例即便没有锁也常因调度侥幸不撞;而 **Desktop + CLI 同时开着**才是这个 bug 最常发生
的场景,那条路径上唯一的保护就是 lockfile。少了跨进程用例,这把锁的**主要用途从未被验证
过**。

做法是把测试二进制自己当成第二个进程(经环境变量分派),两个真实进程对同一个索引目录各写
30 条。反向验证(关掉锁)连跑三次:**34 / 30 / 34**,一次都没到 60 —— 确定性地红。

### AR-R07 已完成(branch `fix/stream-resync`)

复核指出:溢出时服务端只是**断开**,而前端 `EventSource` 连 `stream_reset` 都没监听,重连
后也不取任何权威状态。于是 V2 的 sequence 只能「理论上发现有洞」,实际客户端根本没用它 ——
丢掉的若是 `approval_request`,审批永远不出现,agent 卡在没人看得见的提示上;丢掉的若是
`turn_done`,UI 永远转圈。

三处改动,缺一不可:

1. **权威快照 `GET /snapshot`** —— 除 transcript 外还带 `running` / `plan` /
   `pendingApprovals` / `pendingAsks` / `sequence` / `streamId`。只给 transcript 正是原来
   `/history` 的缺口:那些「只在事件里出现过一次」的状态对不齐。
2. **流上的元信息** —— 开流先发 `stream_ready{streamId,sequence}`(否则客户端收到的第一个
   序号是 7 还是 700 都无从判断);`stream_reset` 带上 `resyncFrom:"/snapshot"` 与断开时的
   `sequence`。用的是命名事件,老客户端的 `onmessage` 不会收到,**向后兼容**。
3. **客户端真的去对齐** —— `stream_reset`、重连、序号断层三种情况都回到 `/snapshot`;
   首屏与「恢复历史会话」也改走同一个 `resync()`,因为两份界面重建逻辑必然漂移。

`internal/eventwire.Stamper` 增加 `Sequence()` / `StreamID()`,与 `eventID` 共用一份流身份
拼法,免得两处漂移。

**一处如实说明的取舍**:原本写了一条端到端「灌爆 SSE 直到服务端断开」的用例,它会挂住 ——
handler 一直在排空订阅,客户端读不读由 socket 缓冲决定,那样的用例只会变成一个偶尔卡死的
测试。改为把契约本身钉死(两个帧的内容、溢出判定、以及内置 UI 的接线),都是确定性的。
内置 UI 那条守卫尤其必要:CI 目前不跑 frontend(AR-R13),而 R07 的价值一半在客户端 ——
服务端把 `stream_reset` 发出去了、客户端不接,等于没修。

Wave B 余下的 AR-R03(dsh session backend)与 AR-R08(envelope / dsh mapping)因 dsh 已
fail-closed 而不再是活跃风险,登记延期。

## Wave C(进行中)—— AR-R12 已完成(branch `fix/turn-scope-wiring`)

复核指出:「四级 Runtime Scope」在 Plan 03 建好、Plan 05 把 Workspace/Session 接上,但
**Turn 一直只是文档骨架** —— `turnState.Guarded` 从 `context.Background()` 派生回合
context,于是关闭会话并不会取消在途的那一轮,得靠 Controller 记得手工 Cancel。少记一次,
就是一个还在跑的 goroutine 抓着一个已经关掉的会话。

`control.Options.Scope` 接收会话的 `runtime.Session`,每一轮在它下面 `BeginTurn()`,回合
context 即 Turn 的 context;正常结束 `End()`,取消也是 `End()`(在 Turn 上这本来就是同一件
事:释放这一轮的资源、取消这一轮的 context,且从不碰它的 session)。

**没传 Scope 的 Controller 行为不变** —— CLI 与大量既有测试都不带 runtime scope,不该
因为这次接线多出一条失败路径。

测试按复核的要求写:关闭会话取消在途回合;取消一轮之后会话仍可用、下一轮能开;关闭一个
会话不影响兄弟会话的回合;没接 scope 时照常运行。外加一条 AST 守卫 ——
`Guarded` 里不得再直接出现 `context.Background()`。这条守卫的必要性在于:改回去之后
**所有行为看起来都正常**,只有「关会话不取消回合」这一个症状,而它极难被注意到。

`AGENTS.md` 那句「`runtime.Turn` is still unwired」已改写 —— 它现在是错的。

### AR-R10 已完成(**上半**;branch `fix/workspace-env-overlay`;下半见后文 C1)

复核指出:`.env` 直接 `os.Setenv` 且「已有值不覆盖」,同进程两个工作区时**先加载的同名 key
永久获胜**。后果不是配置没生效那么轻:用错 key 意味着请求打到别的账号上,或计费记到别人

## C1 已完成(AR-R10 下半;branch `fix/architecture-review-2026-08-21`)

上半把凭据解析挪到了工作区叠加层,但 `.env` 仍然 `os.Setenv` 出去 —— 而**那个导出就是
污染的根**。进程环境只有一份:工作区 A 先加载,`API_KEY=A` 就留在里面,B 的 bash、MCP
插件、语言服务器全都继承到 A 的值。上半之所以还能成立,靠的是一份「哪些 key 是我们导出的」
的包级记录,好在查找时跳过自己写下的东西。那份记录是本轮重构在整个代码库里唯一新增的
包级可变状态,当时就注明了「哪天子进程环境也按工作区组装,这两个变量应当一并删掉」。

现在删掉了。做法不是把 `os.Setenv` 一去了之(那会让用户 `.env` 里的 token 突然对 `gh`、
`docker` 失效,是真回归),而是**谁起子进程谁显式收下这个工作区的环境**:

| 子进程 | 拿到工作区环境的路径 |
| --- | --- |
| `bash` 工具(前台与后台 job) | `boot.Build` 的 `childEnv` → `builtin.ConfineWorkspace` → `bash.env` → `cmd.Env` |
| 钩子命令 | `hook.NewRunner(...).SetEnv(childEnv)` → `SpawnInput.Env` → `cmd.Env` |
| MCP 插件(stdio) | `PluginSpecsIn(cfg.Env(), …)` → `plugin.Spec.BaseEnv` → `mergeEnv` |
| 语言服务器 | `Factory` → `lsp.NewManagerWithEnv(…, cfg.Env().Environ())` → `Manager.clientEnv` |
| CLI 状态栏脚本 | `ctrl.HookRunner().Env()`(与钩子同一份) |

`${VAR}` 展开同样按工作区(`ExpandedPluginIn` / `Env.Expand`),于是两个项目的 `.env` 各配
各的插件密钥,不再抢同一个进程环境。

**Windows 上有一个不写就静默出错的点。** 环境变量名在 Windows 不区分大小写,`os/exec` 的
去重也不区分**且保留最后一个**。若合并时按大小写敏感比较,进程里的 `Path` 和 `.env` 里的
`PATH` 会双双进入切片,子进程最终用到 `.env` 那份 —— 恰好把「进程环境优先」这条语义倒过来。
`envKey` 按平台规范化;并且 `environMerge` 把规范化函数**注入**,所以两条规则在任何平台上
都跑得到,不是只有 Windows CI 才覆盖 —— 否则那条最容易错的分支恰恰最少被执行。

回归测试每条都反向验证过(先破坏实现,确认会红):`.env` 写回进程环境、bash 丢掉 `env`、
`boot` 不再把 `childEnv` 交给钩子、`Factory` 退回 `lsp.NewManager`、插件展开用错工作区、
合并时不做大小写规范化 —— 六处各自对应一条会失败的用例。其中 Factory→LSP 那条没有别的
运行时守卫可依赖:真跑一个 `gopls` 需要 PATH 上有它,CI 上不成立,所以断言的是 Factory
造出来的 manager 带的环境,而 `Manager.clientEnv` 返回的就是 `cmd.Env` 本身。

副作用一则,如实记下:dsh sidecar 的继承白名单读 `os.LookupEnv`,`.env` 不再进进程环境后,
连按名字匹配上的那几个(`PATH`、`HTTP_PROXY` 等)也不会再被项目文件影响。白名单本身未改动
—— 这是收紧,不是放宽。

## B2 已完成(AR-R07 的验收缺口;branch `fix/stream-overflow-e2e`)

复核对 B2 的原话是「强制 overflow E2E 必须证明**最终状态一致且无重复**」。此前这一条只在
两层各测了一半:eventstream 那层证明订阅会被判定溢出,handler 那层证明会走断流分支。
**那之后的事一条都没测** —— 而 AR-R07 的全部意义就在那之后:断流只是止损。

之前放弃端到端的理由是「handler 会尽快把队列写出去,能不能溢出取决于 socket 缓冲」。
那个理由其实站不住:给广播器一个显式的积压上限(`NewBroadcasterWithLimits`),把状态帧
上限压到 8,再让一个真的不读的 HTTP 客户端把 handler 的写阻塞住,溢出就是确定的 ——
`overflow` 标志一旦置起不再复位,所以不存在「灌得不够快」这种概率问题。

用例走完整条链路:接流 → 停止读取 → 灌 2000 条 16KiB 状态帧(≈32MiB,远超任何 socket
缓冲)→ 恢复读取拿到 `stream_reset` → **先接新流再取快照** → 逐号核对。断言是三条:
序号从快照的下一号开始、逐号连续、每个 `sequence` 与 `eventId` 各出现一次。

写这条用例时的两件事,记下来:

1. **第一版是我自己的用例写错了。** 快照之后一次性发 25 条状态帧,只对上 8 条 —— 因为
   上限就是 8,新订阅同样会被撑爆。那是**正确行为**,但测的就不是重新对齐了。改成
   「发一条、等一条」,队列深度始终 ≤ 1,于是「有洞 / 有重复」只可能来自对齐本身。
2. **端到端做下来查出一个真的洞,在客户端那半。** `resync()` 是异步的:`fetch('/snapshot')`
   在飞的时候 `onmessage` 还在照常渲染,而快照一到手第一件事是 `renderHistory` —— 它清空
   整个 log。那个窗口里到达的帧于是被画出来又被抹掉,而快照是更早的一份、并不包含它们;
   `lastSeq` 还会被回退到快照的序号,连断层检测都不会再触发。最坏情况正是 AR-R07 要防的
   那一种:丢的是 `turn_done`,快照里 running 仍为 true,之后又没有新事件 —— 界面永远
   转圈,没有任何东西会去纠正它。

   修法:对齐期间的帧进缓冲,快照应用完之后按序号重放(`sequence <= 快照序号` 的丢弃)。
   实时帧与重放共用 `applyEvent`,不写两份。缓冲有上限,而且**满了不丢** —— 静默丢掉
   状态正是这一层唯一不允许的事,所以满了就再对齐一次,拿一份更新的快照。

守卫的性质说清楚:服务端那条是真行为测试(真 socket、真阻塞、逐号核对);客户端那条是
**接线检查**。`internal/serve/index.html` 是内嵌单文件 UI,没有构建步骤,也不在
`desktop/frontend` 那条 CI 上 —— 用 Go 跑它的 DOM 逻辑需要搭一套 stub,代价与收益不成
比例。所以协议支持这套算法由服务端用例证明,客户端确实照这套算法接线由字符串守卫证明,
两条都反向验证过会红。

| AR-R06 后半 | A5 | Gateway token refresh 必须到达**运行中的** dsh,或触发受控滚动重启 |
| AR-R08.2 / 8.3 | B3 | dsh ToolResult 携带 call ID/name;每个 dsh durable 事件明确映射或降级 |

四条都以「**存在一个跑得起来的 dsh 会话**」为前提。而 `boot.selectEngine` 对
`engine = "dsh"` 是 fail-closed 的(AR-R01),所以这个前提当前不成立:没有 dsh 会话,
就没有 dsh transcript 要解析、没有 dsh 装配要拆、没有运行中的 sidecar 要送 token、
没有 dsh 事件要映射。

强行实现等于写一批**没有任何验证手段**的代码 —— 与任务书 §2「先写能稳定失败的回归测试,
再改实现」直接冲突。所以这里停下来,而不是绕过去。

### fail-closed 不是可以随手撤销的选择

AR-R01 的验收给了两条路:

> - 若支持:dsh 只能提出 tool call,由 OneCreat 执行:`toolpolicy.Before → Tool.Execute → toolpolicy.After → result 回传 dsh`。
> - 若不支持:禁止 dsh 使用 writer/shell/tool execution;装配时明确拒绝不安全配置。

第一条要求 dsh 能**提出一个请求并等 OneCreat 回答**。本仓库对接的 dsh
`@deepseek-ai/dsh-sdk-jsonrpc-server`(0.1.0-rc.7)协议里没有这个通道:

- `internal/engine/dsh/protocol.go` — client→server 只有三个请求
  (`initialize` / `session/prompt` / `shutdown`);server→client 只有四个**通知**
  (`session.event` / `session.status` / `subagent.started` / `subagent.finished`)。
  JSON-RPC 的通知没有 id、不期待回复。
- `internal/engine/dsh/linerpc.go:90` — 读循环只认两种入站帧:**响应**(有 id 且带
  result/error,投给我们自己发出的等待中请求)与**通知**(有 method,无回复路径)。
  没有「入站请求」分支,`LineClient` 上也没有任何 respond/reply 方法。

所以 `tool/call` 到达时,工具**已经在 dsh 自己的进程里跑完了** —— 文件已写、shell 已执行。
事后看一眼不是门禁。这正是 AR-R01 的原话:「不得在工具已经执行后,根据 `tool/call` 显示
事件做事后审批。」

限定一句:以上是对**本仓库当前对接的那个版本**的判断。上游 dsh 之后是否加了 server→client
请求通道,本会话无法从这里核实。

### 最小决策建议(需要用户裁决)

三条路,按代价从小到大:

1. **维持 fail-closed,四条 finding 标为「等上游协议」。** 代价:`internal/engine/dsh`
   保持「已接线、未放行」;Plan 12 的 `TurnEngine` 边界仍然成立并有守卫。这是当前状态,
   也是唯一不牺牲安全语义的一条。
2. **推动 dsh 上游加 `tool/execute` 请求(server→client,带 id、等回复)。** 拿到之后
   A1 的第一条路才走得通,B1/B3 随之有意义;A4/A5 也才有验证手段。这是唯一能真正关闭
   四条 finding 的路,但依赖本仓库之外的改动。
3. **放行一个只读 / 纯模型的 dsh 档位**(禁用 writer 与 shell)。能让 dsh 跑起来从而给
   A4/B1/B3 提供验证场景,但需要 dsh 侧能按能力裁剪工具集 —— 同样要上游支持,且价值有限。

**不建议**的一条:给 fail-closed 加配置开关放行完整 dsh。能被一行 TOML 关掉的安全门不是门,
而这正是 AR-R01 的核心结论。

## §23 AR-R02 的最后一格:unsupported 的 HTTP 状态码

复核对 AR-R02 的验收有三句,前两句上一轮做了(后端在改任何状态之前拒绝、Controller 暴露
只读 `Supports`),第三句我漏了:

> HTTP 返回明确 409/422;Desktop/CLI 禁用并显示原因;**后端校验不能依赖 UI**。

漏的后果不是"不够漂亮"。那些端点原来一律回 **500**,而 500 的含义是「服务器坏了,可以
重试」—— 对一个引擎干不了的操作,事实恰恰相反:重试多少次都一样。照状态码行事的客户端
(重试队列、自动化脚本、任何不读中文响应体的东西)会一直撞下去。语义错的状态码,和不给
原因差不太多。

两条必须**分开**,这是这次改动的全部要点:

| 情况 | 码 | 客户端该怎么办 |
| --- | --- | --- |
| `engine.UnsupportedError` | **422** | 这个引擎永远做不到,**别重试** |
| `control.BusyError`(有回合在跑) | **409** | 状态冲突,**待会儿可以再来** |
| 其它 | 500 | 确实是服务端的问题 |

混成一个码等于告诉客户端「我分不清你该不该重试」。为此给「忙」加了类型化的
`control.BusyError`(文案一字未改,只是从 `fmt.Errorf` 变成有类型),映射用 `errors.As`
而不是字符串前缀 —— 控制层随时可能给错误加一层上下文,靠字符串匹配的映射会在那一天悄悄
退回 500,而且没有任何测试会红。专门有一条用例锁住"包装之后仍然认得出"。

`/snapshot` 同时带上 `engine` 与 `capabilities`,前端据此禁用做不到的入口**并说明原因**,
而不是让用户点下去撞一个 422。能力清单由 `engine.All()` 提供 —— 单一真源,否则 serve 与
desktop 各抄一份常量,加一个能力时必然漏掉某一份。**后端仍然独立校验**:UI 从来不是安全
边界,这里给的只是"显示原因"所需的数据。

一处如实说明:409 那条测的是映射函数本身,不是端到端。`Compact` / `NewSession` 在
`executor == nil` 时提前返回,而 serve 的测试装配里没有真 `agent.Agent`,端到端根本走不到
忙碌分支;与其搭一个真 executor 只为造一个状态,不如直接测那段逻辑 —— 而"映射确实被这些
端点用上了"由 422 的端到端用例证明。

三条守卫都反向验证过:映射退回一律 500、改用字符串前缀匹配(包装后失效)、快照不带能力表。

## §24 C1 的完整性缺口:装配后期追加的插件没拿到工作区环境

这是我自己在 C1 里漏的一处,复审「残留限制」那一栏时查出来的 —— 记下来,因为它正是
C1 那条注释警告过的失败形态,而我一边写下那句警告,一边漏了两处。

`PluginSpecsIn` 给**配置里**的插件装上了本工作区的环境。但有两类 spec 是在那之后才被
追加进来的:

- **codegraph** —— 装配时解析到二进制才注入,是「又一个 stdio 插件」;
- **`opts.ExtraPlugins`** —— ACP 客户端在 `session/new` 里指名的服务器。

它们的 `BaseEnv` 是 nil,于是退回进程环境。C1 之前那没问题(`.env` 就在进程环境里),
C1 之后就成了**静默失效**:同一个会话里,配置里的 MCP 服务器拿得到项目 `.env`,这两类
拿不到 —— 而且不会有任何报错。

修法是在 stderr 那一遍旁边并排加一遍 `applyChildEnv`,只填 nil 的那些(调用方显式给过
`BaseEnv` 就是它的决定,不覆盖)。放在那里不是随手:哪天加了第四个 tier 而漏掉这一遍,
**stderr 也会一起坏**,不会只坏这条安静的。

同时把「这个工作区的插件该用什么基础环境」收成一个 `workspaceBaseEnv` —— 没有 `.env`
叠加层就返回 nil(继承进程环境,改动前的行为)。原来这条规则藏在 `PluginSpecsIn` 里,
后期追加那一遍要是自己再判断一次,两处迟早分叉。

端到端守卫:用测试二进制自己当一个最小 MCP stdio 服务器,把它**子进程里**看到的
`C1_MCP_KEY` 编进工具名,父进程从 `ctrl.ToolNames()` 读回来。为什么必须真起进程 ——
`BaseEnv` 有没有被填上,读一下结构体字段就知道;但那证明不了子进程**看见**了什么,而这次
的 bug 恰恰是「字段没填,于是子进程看的是进程环境」。反向验证(去掉那一遍)确定性地红。

## §25 AR-R02 的第三句后半:入口要禁用**并说明原因**

§23 做了「HTTP 返回明确 409/422」。同一句话还有后半:

> Desktop/CLI **禁用并显示原因**;后端校验不能依赖 UI。

只到「后端回 422」是不够的,而且不是体验问题:用户看到一个可点的 "New Session",点下去
界面毫无变化(错误只在响应体里),于是以为自己点错了,反复再点。

内置 UI 现在从权威快照读 `capabilities`,把四个依赖能力的入口(新建会话 / 压缩 → `resume`,
回退 / 分支 → `fork`)按能力禁用,`title` 里写清是哪个引擎缺哪条能力。映射集中在一处
`CAP_GATED`,不在四个按钮上各写一遍 —— 那种写法加第五个入口时必然漏掉。

必须同时说清另一半:**这不是那道门。** 后端的 `requireCap` 在改任何状态之前独立校验,
把这段全删掉也放行不了任何操作。这里做的只是「别让用户白点」。

### 这条守卫这次不是字符串匹配

之前 `internal/serve/index.html` 的守卫都是接线检查(它没有构建步骤,也不在
`desktop/frontend` 那条 CI 上)。字符串匹配能确认「这几根线还在」,但布尔取反、属性名写错、

这次把 `CAP_GATED` / `applyCapabilities` / `gatedIsBlocked` 三段从 HTML 里抽出来,配一个

四条反向验证全部确定性地红,而且**其中三条是字符串守卫抓不到的**:布尔取反、title 不清理、

如实说明:**没有 node 就跳过**,所以它不在 Go 那条 CI 腿的覆盖里。它的价值在开发机上 ——
改这段逻辑时立刻会红,而不是等到有人在浏览器里发现按钮点不动、或该禁的没禁。

## §26 把 B2 的客户端那半从「接线检查」升级成行为测试 —— 结果当场抓出一个真 bug

§25 证明了一条路可行:把内置 UI 的一段逻辑抽出来,配一个 DOM 桩,在 node 里真跑。既然
可行,B2(§ 「B2 已完成」)里那句自我限定就不该留着 ——

> 客户端那条是**接线检查**,不是行为测试。

字符串匹配确认不了的东西,恰恰是那个修复的全部要害:缓冲里的帧有没有按序号重放、
`<= 快照序号` 的有没有被丢掉、缓冲满了会不会静默丢状态。

### 它抓出了什么

第三组断言当场红了:**缓冲溢出后的重试对齐,状态被前一次的收尾清掉了。**

`resync()` 的结构是 `fetch().then(...).catch(...).finally(...)`。溢出重试是在 `.then` 里
**同步**发起下一次 `resync` 的,而先前那次的 `.finally` 排在它之后才跑 —— 于是刚建好的
`resyncing=true` / `resyncBuf=[]` 被抹成 `false` / `null`。后果:第二次对齐期间到达的帧
根本不会进缓冲,照旧被渲染、再被 `renderHistory` 抹掉。**正是 B2 要修的那类 bug,藏在
B2 的修复自己里面。**

修法不是给这一条路径打补丁,而是修根因:给每次对齐一个代号 `resyncGen`,`.finally` 只有
在自己仍是"当前那一次"时才收尾。任何形式的重入都不会再被过期的收尾清掉。

### 反向验证(四条,全部确定性地红)

| 破坏点 | 字符串守卫 |
| --- | --- |
| 退回无代号的 `.finally`(就是刚抓出来的那个 bug) | 抓不到 |
| 退回边收边渲染(不缓冲) | 抓得到 |
| 重放时不丢弃 `<= 快照序号` 的帧(制造重复) | 抓不到 |
| 缓冲满了照旧重放半截 | 抓不到 |

四条里三条是纯字符串守卫做不到的。

### 一句该记住的

这一轮里,**两条**新守卫各自抓出一个已经提交进分支栈的真 bug(§24 的插件环境、这里的
对齐重入)。它们都不是"新写的代码有问题",而是"旧守卫太弱,所以问题一直在那儿没人发现"。
守卫的强度本身就是可以复核的对象 —— 一条永远绿的守卫和没有守卫,区别只在心理上。

如实说明:与 §25 那条一样,**没有 node 就跳过**,不在 Go 那条 CI 腿的覆盖里。

`ci.yml` 的 `pull_request.branches` 过滤的是 **base**,名单是

## §29 AR-R03 后半:转录文本的真源属于引擎

`sessionStore.save()` 原来无条件把 OneCreat 侧的消息日志写成 `.jsonl`。引擎自己持有会话时
(dsh 今天就是),那份文件是赝品 —— 复核 AR-R03 的原话:「不得双写或用空 native JSONL
冒充 dsh」。

判据用现成的 `CapResume`(定义就是「会话状态可以从 OneCreat 侧的消息日志恢复」),不新造
能力常量:不声明它 → 不落盘 → 记录标 `Ephemeral`,身份/项目/真实引擎名照留。

**一处我自己写错、被旧测试抓回来的**:第一版让不落盘的引擎完全不登记记录。但复核要的是
「Registry 记录真实 engine、stable session ID … UI 标记 ephemeral」,抹掉记录方向反而错了。
`TestSessionRecordCarriesTheRealEngine`(#15 自己写的那条)当场变红。写下来是因为这类
「修过头」比漏修更难自查 —— 它看起来更严格。

`Registry.Ensure` 签名未动(desktop 四个调用点零改动),新增并列的 `EnsureEphemeral`。

## §30 AR-R08.2 / 8.3:我按「属于哪个组件」分类,而不是按「验证它需要什么」

这两条此前和 AR-R05 一起被我标成「dsh 专属,被协议阻断」。`dsh.Map` 是个纯函数,喂结构体
就能测,从来不需要一个跑得起来的 sidecar。**连着两次(AR-R03 后半、这两条)都是同一个错误
分类方式导致的**:按组件归属判断「能不能做」,而不是按「验证它需要什么」。

两个具体缺陷:`EvToolResult` 丢掉 `callId`/`name`(并行调用的结果对不回号,失败结果会挂到
别的卡片上);`default: return nil` 静默吞掉 `todo/*` `step/*` `compaction/*`。

降级而非硬猜:三族状态事件映射成带类型名的 `Notice`,可见但不假装理解载荷;未知类型仍不
产出事件(可能是高频流式事件)。网关红线单独一条用例锁住,反向验证会红。

## §31 AR-R06 后半:token 刷新到不了一个已经在跑的 sidecar

token 在 `Boot` 时烤进子进程环境,进程一起来就冻住;dsh 协议里没有换 token 的方法。复核
给的两条路里第一条不存在通道,所以走第二条 —— 受控滚动重启:`Options.Credentials` 收一个
**活的**凭据源,每轮开始前与烤进去的那份比一次,变了就复用 AR-R04 的终结状态标死,由调用方
重建。

两条边界:凭据源报错/空串不动会话(一次抖动变成「会话没了」比多跑一轮糟得多);没配
`Credentials` 的调用方行为一字节不变。

**又一次自查记录**:那条守「报错不该打死会话」的用例第一版不带 token 启动,而 `bootToken`
为空时判断走不到 —— 反向验证时它照样绿。一条不会红的用例等于没有。这是本轮第三次靠反向
验证抓到自己的问题(前两次:AR-R03 修过头、AR-R08 分类错)。
