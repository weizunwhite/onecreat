## 1. 文档目的与事实源规则

这份文档是 OneCreat 本轮架构重构的主执行计划，用于约束 ChatGPT、Claude Code、Codex 以及人工开发者后续的修改范围、顺序、测试和验收。

本轮重构的目标不是重写项目，也不是微服务化，而是在保持现有产品行为的前提下，逐步修正已经出现的架构边界问题，使 Desktop / CLI / Serve / ACP / 未来 dsh 能共享同一套清晰的运行时模型。

### 事实源优先级

执行架构重构任务时，按以下顺序理解仓库：

1. 当前分支真实源码与测试；
2. 本文件 `docs/架构重构执行总计划.md`；
3. 根目录 `AGENTS.md` 的工程约束与红线；
4. 其他历史文档与提交说明。

若 `AGENTS.md` 中存在本轮重构前的旧架构描述，例如“Desktop / Serve 分别维护 event wire 映射”，以当前源码和本计划为准；但 `AGENTS.md` 中关于双 Go module、Session 单写者、DeepSeek prefix cache、Checkpoint、硬件安全等工程约束仍必须遵守。

### 执行规则

- 每个 Plan 独立分支 / 独立 PR，除 Plan 00 当前已存在于 PR #2 外。
- 一个 Plan 只解决该 Plan 明确列出的架构问题。
- 不允许为了“顺手整理”扩展范围。
- 每个 Plan 必须先建立或确认回归测试，再修改实现。
- 每个 Plan 必须完成 diff 自审、跨平台 CI、已知风险说明后才能进入下一个 Plan。
- 不得因为 CI 基线已有红项而伪装为“本 PR 全绿”；必须区分新增回归与基线问题。

# 2. 当前架构概况

OneCreat 当前是 Go 重写后的多前端架构：

```text
CLI / TUI     HTTP / SSE     ACP     Wails / Web Desktop
     \            |           |             /
                  control.Controller
                         |
                     agent.Agent
                         |
                 Provider / Tool Registry
```

根模块负责 kernel、CLI、命令行工具；`desktop/` 是独立 Wails Go module。

当前已有一些值得保留的边界：

- `provider.Provider` 小接口 + registry；
- `tool.Tool` + per-run registry；
- `event.Sink` 作为内核向前端的单向事件边界；
- Session 的单写者模型与 Snapshot 约束；
- Checkpoint / rewind 的现有行为约束；
- DeepSeek prefix cache 的 append-only prompt 设计。

本轮重构不应无理由破坏这些边界。

# 4. 目标架构

目标不是引入更多层级，而是把 Transport、Application、Runtime Scope、Engine Adapter 明确分开。

```text
Transport
CLI / TUI / Wails / HTTP / SSE / ACP
                    |
                    v
Application
ChatService / SessionService / WorkspaceService / ApprovalService
AccountService / HardwareService / KnowledgeService / SettingsService
                    |
                    v
Runtime
ProcessRuntime
  └─ WorkspaceRuntime
       └─ SessionRuntime
            └─ TurnRuntime
                    |
                    v
Engine + Adapters
NativeEngine / DshEngine
Provider / Tool / MCP / Stores
```

## 四级资源作用域

### Process scope

建议承载：

- Account session；
- CredentialSource；
- HTTP clients；
- Updater；
- 全局不可变 catalog / factory。

### Workspace scope

建议承载：

- 显式 `Root`；
- workspace config；
- sandbox root；
- skills / memory index；
- CodeGraph；
- LSP；
- workspace MCP；
- workspace-level tool capability。

### Session scope

建议承载：

- Conversation；
- Session metadata；
- Checkpoint journal；
- Approval broker；
- session-specific MCP overlay；
- plan / coach / bypass 等会话状态。

### Turn scope

建议承载：

- `context.Context`；
- cancel handle；
- 当前模型请求；
- tool batch；
- usage；
- 临时 evidence / per-turn state。

# 5. 不可违反的重构红线

1. **不重写整个项目。**
2. **不微服务化。**
3. **一次只解决一个架构层。**
4. **不为了目录漂亮而大规模搬文件。**
5. **Workspace / Tab 边界完成前，不正式迁移 dsh。**
6. **不创建覆盖所有产品能力的巨型 Engine 接口。**
7. **不新增进程级隐藏全局状态。**
8. **先保持行为等价，再做功能增强。**
9. **不得破坏 Session 单写者 + Snapshot 约束。**
10. **不得把 per-turn runtime state 放入 DeepSeek cached system prefix。**
11. **任何会重排 Session message log 的改动必须继续正确处理 checkpoint boundary 失效。**
12. **安全 / Permission / Billing / Hardware honesty 行为不得在无明确计划时顺手改写。**

# 9. Plan 01 — 显式 WorkspaceContext

## 对应问题

A01。

## 目标

从：

```text
Workspace == process cwd
```

改为：

```go
type WorkspaceContext struct {
    Root string
}
```

Workspace root 必须显式传递，不再通过 `os.Chdir()` 表达运行时业务状态。

## 实施步骤

1. 全仓枚举 Workspace 语义下的 `os.Getwd()` / `os.Chdir()`；
2. 区分“进程启动默认目录解析”与“运行时 workspace 状态”；
3. 建立最小 `WorkspaceContext`；
4. 将 root 显式传入 config、sandbox、file tools、bash、MCP、skills、memory、session 等真正依赖 workspace 的路径；
5. 保留必要的启动兼容逻辑，但运行时 workspace 切换不得再调用 `os.Chdir()`；
6. 新增双 workspace 并发隔离测试。

## 必须新增的特征测试

至少覆盖：

```text
Workspace A: a.txt
Workspace B: b.txt
```

- A 的 bash `pwd` 始终是 A；
- B 的 bash `pwd` 始终是 B；
- A 的 file write 不能落到 B；
- B 的 file read 不能越到 A；
- A / B 两个 runtime 可同时存在；
- 切换活动 UI workspace 不改变后台 session 的 root。

## 禁止修改

- 不拆 Controller；
- 不引入 dsh；
- 不重做 Session Store；
- 不改前端交互形态，除非为显式 workspace identity 必须增加最小 DTO。

## 核心验收

**运行时 Workspace 创建、切换和多 workspace 并存不再依赖 `os.Chdir()`。**

## 状态

**已完成（2026-08-20）**，等待人工确认。分支 `refactor/workspace-context`，Draft PR #3
（base = `refactor/runtime-context-tabs`,即 Plan 00 的分支——Plan 00 尚未合并，
所以 Plan 01 以栈式 PR 叠在其上，保证每个 PR 的 diff 仍只含本 Plan 的改动）。

### 实现要点

1. 新增 `internal/workspace`：`Context` 是不可变、恒为绝对路径的工作区身份，
   零值 = 「无显式 workspace」= 进程 cwd 语义（CLI 保持逐字节不变）。
   root 是**非导出**字段 + 构造函数，杜绝「可被重新赋值 / 可以是相对路径」的
   workspace——那正是本 Plan 要根除的 bug 形态。
2. `config.LoadIn(ws)`：四个项目级文件（`reasonix.toml` / `onecreat.toml` /
   `.mcp.json` / `.env`）按 workspace 解析；`Load()` 退化为 `LoadIn(零值)`。
   `Config` 记住自己是从哪个 workspace 加载的，`WriteRoots()` 默认根随之而变。
3. `boot.Options.Workspace`：memory、skills、CodeGraph（`EnsureInit` + MCP 子进程
   `Dir`）、LSP、hooks、`Controller.WorkspaceRoot` 全部改用它。
4. `builtin.ConfineWorkspace(workDir, roots, bash, search)`：一次性把**所有**
   workspace 相关内建工具（读、写、bash、ls/glob/grep）绑到工作区。此前 `addBuiltins`
   只替换了写工具/bash/grep，**读工具（`read_file`/`ls`/`glob`）仍按进程 cwd 解析**——
   这是原实现的隐性缺口，本 Plan 一并补上。
5. `control.Controller`：`cpRoot` 更名 `wsRoot`（同一个字段、语义变诚实），
   `connectCodegraphMCPServer` 不再 `os.Getwd()`。
6. 桌面端：
   - `tabRuntime.ws` —— **每个标签持有自己的工作区根**，是该标签运行时的真源；
   - `App.ws` —— 「当前选中的项目」（新标签在哪开、对话框从哪起、UI 文件浏览按哪解析），
     与 `tabRuntime.ws` 是**不同概念**，不是镜像；
   - `ensureWorkspace()` → `resolveStartupWorkspace() workspace.Context`：
     仍在启动时 chdir（计划允许的启动兼容），但把结果作为显式 Context 返回；
   - `SwitchWorkspace` **不再 `os.Chdir`**，因此**删除了「开着多个标签就拒绝切换项目」
     的历史限制**——那条限制的唯一存在理由就是进程级 cwd；
   - 5 个 `boot.Build` 调用点（buildTab / SwitchWorkspace / SetModel /
     rebuildTabByID / settings rebuild）全部传该标签自己的 workspace，
     避免「换个模型就把标签的项目根悄悄挪回进程 cwd」；
   - 13 处 workspace 语义的 `os.Getwd()` 改为跟随选中项目。

# 10. Plan 02 — 真正的 TabManager

## 对应问题

A02。

## 目标

消除：

```text
tabs[id].ctrl
+
App.ctrl / App.sink / App.model / App.label / App.ready / App.startupErr
```

两套活动标签真源。

建议：

```go
type TabManager struct {
    activeID string
    tabs map[string]*TabRuntime
}
```

## 实施原则

- `tabs[id]` 是唯一 runtime 真源；
- Active tab 只是 `activeID`，不再复制 controller / model / sink 等对象；
- 后台 tab 操作必须显式通过 tab ID 路由；
- 旧前端未传 tab ID 的入口只能在 transport facade 读取 `ActiveID()` 后委托；
- `boot.Build` 等慢操作不得持 TabManager 全局锁。

## 必须测试

- build tab 期间切 active tab 不串 controller；
- build tab 期间关闭目标 tab，创建出的 runtime 会被正确 Close；
- background approval / event 不进入 active tab；
- 并发 Create / Close / SetActive 不产生 race；
- `go test -race` 覆盖关键路径。

## 验收

`App.ctrl` / `App.sink` / `App.model` 等不再作为活动标签镜像存在。

## 状态

**已完成（2026-08-20）**，等待人工确认。分支 `refactor/tab-manager`，Draft PR #4
（base = `refactor/workspace-context`，栈式叠在 Plan 01 上）。

验收确认：在 `desktop/` 下 grep `a.ctrl` / `a.sink` / `a.model` / `a.label` /
`a.ready` / `a.startupErr` / `a.activeTab` / `a.tabOrder` / `a.tabSeq`
——**零命中**，这些字段已从 `App` 上彻底消失。

### 实现要点

1. 新增 `desktop/tabmanager.go`：`tabManager` 拥有 `tabs` / `order` / `active` / `seq`
   和自己的锁；`tabRuntime` 也搬了过去。`App` 只剩 `tabs *tabManager`。
2. **「活动标签」只是一个 id**。`SetActiveTab` 从「重指 6 个镜像字段」变成一行
   `a.tabs.SetActive(id)`——没有需要一并同步的副本，也就不存在「漏同步某个字段 →
   指令打到已关闭的 controller」这类 bug。
3. 读取一律走快照：`View(id)` 在锁内产出不可变的 `tabView`，调用方不再持有
   `*tabRuntime` 裸指针跨锁读字段。`Ctrl(id)` / `Sink(id)` 是它的窄封装。
4. 写入一律走 `Update(id, fn)`（锁内改、回报该标签是否为活动）。所有
   `boot.Build` 后的回写都按【发起时的 id】落回，用户 build 期间切走也不串标签（A5）。
5. **两把锁互不嵌套**：`a.mu` 只保护 App 自身的 `disabledMCP` / `mcpOrder` / `ws`，
   标签运行时归 `tabs` 自己的锁；`boot.Build` 这类秒级操作绝不在任一把锁内调用。
6. **删掉了冗余的 `tabRuntime.closed` 标志**：「从注册表移除」本身就是关闭信号，
   在途 `buildTab` 的写回落空即知该自行 `Close`。两个信号意味着两处要记得同步 ——
   正是本 Plan 要消除的形态。
7. 修掉一处过程中发现的竞态：`buildTab` 原本分两次加锁判断「是否被采纳」，
   与 `CloseTab` 并发时两边都可能认为该由自己 `Close`（双重 Close）。改为在同一次
   `Update` 里定下来——`Update` 找得到 ⟺ 标签还活着 ⟺ 这个 controller 归它。

### 特征测试（`desktop/tabmanager_test.go`）

- `Register` 即激活、顺序与 active 标志正确；
- `""` 在**读取时**解析为活动标签（切换后立刻生效 → 证明不是缓存）；
- 关掉未知 id / 关掉最后一个标签的边界；
- **A6**：`Close` 后在途 build 的写回必须落空（它据此自行 `Close`，不泄漏）；
- **A5**：build 期间切走，重建结果仍落回发起标签、不串到用户切过去的那个；
- **并发**：8 goroutine × 50 轮 create/update/read/switch/close，`-race` 下必须干净；
- nil receiver 读取安全（与包内裸 `&App{}` 测试惯例一致）。

原有的 `tabs_test.go` 断言从「镜像字段是否被重指」改写为「解析是否落到正确的标签」——
断言的是行为，不是已被删除的实现细节。

### 验证结果

PR #4 head `65fce1c`（CI run `32401485722`）——**5/5 全绿**：
Ubuntu / macOS / Windows / Desktop / Race。

本地补充：desktop `gofmt` / `go mod tidy`（无漂移）/ `go vet` / `go test` /
**`go test -race`** / `go test -tags web` 全绿；`GOOS=windows go vet ./...` 通过。
root module 本 Plan 零改动。

### 本 Plan 明确**未**处理

1. `desktop.App` 仍是 God Object（硬件/知识库/账号/设置/更新全在里面）——**Plan 06**；
2. `App.ws`（当前选中的项目）与各标签的 `ws` 是**不同概念**、不是镜像，保留；
   Process / Workspace / Session / Turn 的正式分层是 **Plan 03**；
3. `control.Controller` 未拆——**Plan 07**。

# 25. 最终成功标准

本轮架构重构完成后，OneCreat 应满足：

- Workspace 是显式对象，不是 cwd；
- Tab 只有一个 runtime 真源；
- Process / Workspace / Session / Turn 生命周期清晰；
- Desktop / CLI / ACP 共享统一 RuntimeFactory；
- App 与 Controller 变成薄 facade / application orchestration，而不是 God Object；
- Agent 主要负责模型与工具执行循环；
- Account / Gateway 不再通过进程 env 作为状态总线；
- Event 协议有单一 schema、sequence 与可靠关键事件语义；
- Session / Persistence 只有一个明确对话真源；
- Native 与 dsh 通过最小 Engine abstraction 接入；
- dsh 不复制 OneCreat application core；
- Linux / macOS / Windows / Desktop / Race CI 均能稳定保护上述边界。
