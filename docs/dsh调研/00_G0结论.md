## 一句话结论

**网关可行(有 2 高 2 中可堵漏点);dsh 是更强的通用底座 + 官方生态,但在我们的硬件/诚实性护城河上开箱不更强、且"明显更强"未能实测;建议"有条件进 Phase 1 spike"——先做工程打通与网关堵漏验证,把"是否全量迁移"的最终拍板压后到:①拿到凭证补跑 Step 3 在线对比;②spike 证明护栏可低成本迁移。**

## 1. 网关:可行 / 不可行 + 要堵的漏点清单

**结论:可行,但需堵 4 处漏点(2 高 2 中),其中"隐藏 provider 品牌名"需一个薄 TS 适配器插件、非纯配置。**

- ✅ **配置层可行**:dsh 的 `dsh-llm-deepseek` 是 OpenAI 兼容 chat-completions 客户端,`baseURL`(可指网关)+ `apiKeyEnv`(只存环境变量名,不入提交文件)+ `Authorization: Bearer`,与我们现有 `POST /api/onecreat/v1/chat/completions` 契约对齐,**指向网关无需改源码**。wire `model` 由驱动方每会话下发,应下发**档位占位符**而非真名。

| 漏点 | 严重度 | 堵法 |
|---|---|---|
| ① 真实 model/provider 名落进 durable 会话日志(`request/header`/`request/context`)且经 `session.event` 全量流出、落盘(JSONL/SQLite) | **高** | wire model 下发档位占位符 + Go 驱动层擦 `request/header`/`request/context` + 保证 dsh store 落盘只存占位符 |
| ② Web UI 有 model-selector/settings/凭证面(**运行时实证:首启即弹"API 密钥"输入框**) | **高**(仅当用 dsh Web UI) | 不用 dsh Web UI(规划非目标),headless/SDK profile 不组合这些 UI 包;`models: []` 关 catalog 广播 |
| ④ provider 路由名 `deepseek-official` 硬编码,凡日志/事件/UI 出现 provider 字段即暴露"底层是 DeepSeek" | **中-高** | 需写一个**自命名薄适配器插件**(路由名 `onecreat-gateway`)隐藏品牌——**这条无法纯配置** |
| ③ 传输错误体带 `baseURL`(网关 URL) | **中** | Go 驱动层脱敏;错误体不含 model 名 |

> 详见 `02_网关接入验证.md`。**比规划 Phase 2.3 多一件事**:隐藏 provider 品牌需薄插件,不止"Go 驱动层过滤"。

## 2. 能力:dsh 明显更强 / 相当 / 更弱 —— 证据是哪张表

**结论:证据不足以判定"明显更强"(在线跑分未做);按 `03` §3 的结构对比表,dsh 是"更强通用底座 + 更全子代理/插件生态 + 官方维护",但在我们的产品轴(弱模型硬件编程 + 诚实性护栏 + 证据链 + 账号档位)上开箱并不更强——那些护栏正是 dsh 没有、我们过去一年投入的东西。**

- 证据表:`03_实测对比.md` §3(能力/诚实性结构对比)。
- 已完成的本地实证(不需模型):ESP32 编译链可用(296KB blink 干净过)、硬件 MCP 是合规 stdio server(27 工具)且零改动可挂 dsh(§2/§3)。
- 关键判断:**迁移的价值是"继承 DeepSeek 官方通用底座 + 生态 + 维护",不是"硬件任务即时变强"**。要达到"至少持平",**必须把现有护栏(板卡事实注入/诚实收尾/证据引擎)迁到 dsh 扩展点上**——接入点都已在源码中定位到(MCP、`tools/*` 钩子、`agent/pre-step` 注入、skills、`todo/write`+`tool/result` 事件)。

**对闸门 G0 原判据**:规划文档 G0 = "0.2 可行 **且** 0.3 明显更强"。严格读:0.3"明显更强"**未实测、且结构上开箱不更强 → 严格版 G0 不满足**。执行提示词 Step 5 分支 A 的放宽条件 = "网关可行或仅有可堵漏点,**且 dsh 能力明显更强或相当但生态/官方维护价值明确**" → **宽松版满足**(相当 + 官方/生态价值明确 + 网关可堵)。

## 3. 建议:进 Phase 1 / 不迁 / 需补哪些验证再定

**建议:有条件进 Phase 1 spike(工程验证),但不承诺全量迁移。** 理由:

- 网关可堵、嵌入路径存在、硬件 MCP/证据引擎接入点都已证实 → 工程上可打通,值得用一个隔离分支的 spike 验证成本。
- 但"明显更强"未证 + 护城河需整体迁移 + dsh 是 developer preview(**无兼容承诺、SDK 协议 0.0.1、单一 wire 覆盖不全我们的 Controller**)→ **不应据此就承诺全量迁移**。

**进入 Phase 2(护城河搬迁)之前必须先满足的补验证**:
1. 拿到任一凭证,补跑 `03` §6 的 A/B 在线对比(尤其 T5 诚实拒绝、T1/T4 不谎报),用数据回答"是否明显更强/持平"。
2. spike 证明证据引擎 + 板卡事实注入 + 诚实收尾护栏能以**可接受成本**迁到 dsh 扩展点(否则诚实性退化,迁移得不偿失)。
3. 平台侧确认网关容忍 dsh 归因头(`User-Agent`/`x-deepseek-harness-*`)、并正确按占位符 model + token 做 tier 映射。

## 4. 进 Phase 1 若干"规划文档没写到"的风险与工作量修正

1. **单一 wire 覆盖不全 Controller(最大低估)**:SDK JSON-RPC 流式保真但**无 cancel、审批 dead capability、无 resume/fork wire**;ACP 有 cancel+审批但**只推 committed 消息(无流式/工具事件/plan)、仅新会话**。→ Phase 1 要么"SDK 流式 + 进程杀取消 + 组合层自动审批策略",要么"ACP 交互 + 牺牲流式",或**混用两协议**。规划把 Cancel/Approve/SetPlanMode/Resume 当"实现最小子集"轻描淡写,实际它们**在 wire 层就有硬缺口**。
2. **审批**:自动化(headless)可用 sandbox/approval 策略自动批,能满足"跑通 ESP32 编译题";但**桌面端交互审批**必须走 ACP 的 `request_permission`,而 ACP 又丢流式——这是需要产品取舍的架构分叉,不是纯工程。
3. **plan 模式**两 wire 都不直接驱动(需命令面/注入)。
4. **隐藏 provider 品牌名需薄适配器插件**(见 §1 漏点④),非纯配置。
5. **证据引擎是诚实性唯一来源**,必须随迁,不能后置成"锦上添花"(`03` §4)。
6. **文件级 checkpoint/rewind**(`internal/checkpoint`)dsh 无等价物,需保留 Go 实现或明确放弃。
7. **打包体积**:Go 单静态二进制 → 需捆 Node 运行时/bundled dsh 分发(rc.7 首装即 GB 级 npx 缓存);Windows 后置。
8. **安装坑**:`npx @deepseek-ai/dsh` 首次并发运行会撞 npm cache 权限(`EACCES/EEXIST rename`),需隔离 cache;首启构建以分钟计、期间无 stdout。

## 5. pi 作为 B 计划的结论

本次 **G0 走宽松版进 Phase 1(分支 A)**,未触发 B 计划,故**未对 pi 做对照**。若后续补验证(§3)结论转为"不迁 dsh",再按执行提示词分支 B 用 pi 走一遍并补 `05_pi对照验证.md`。当前一句话:pi(`pi-mono` / `pi-agent-core`)有 RPC 模式与多 provider,但**产品 DeepSeek-first + dsh 是模型厂自家 harness**这两点仍让 dsh 优先级高于 pi;dsh 唯一的战略劣势是 developer preview 的不稳定性。
