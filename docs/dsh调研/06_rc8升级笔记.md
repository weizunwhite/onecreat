### 必须改的清单

1. **`dsh/plugins/control/index.js` 补 loader await**(对应上游 sdk/server 的那 6 行)。
   我们的控制面自己拥有 transport、自己分派 `initialize`,拿不到官方 `apply()` 里的修复。
   而我们**恰恰**在同一个 `apply()` 里 `ctx.plugin(McpClient, …)` 挂硬件 MCP —— 这正是上游注释
   点名的场景(MCP 首轮工具发现是异步 Loader 条目)。不补,`initialize` 可能在硬件工具注册完成前
   就应答,首轮出现"工具还没挂上"的窗口期。
2. **版本号锁到 rc.8**:`dsh/package.json` 22 个 `@deepseek-ai/dsh-*` 依赖 + 重新生成 `pnpm-lock.yaml`。
3. **新的品牌串风险(rc.8 引入)**:`llm-deepseek/src/adapter.ts` 新增两条面向用户的错误文案,
   都以 `DeepSeek` 开头 —— `DeepSeek model "…" does not accept image input.` 与
   `DeepSeek image conversion requires the durable attachment service.`。
   只在"请求内容里含 image 块"时才触发,OneCreat 当前不往 dsh 送图片(Go 侧只发 text 块),
   所以触不到。核过 `internal/boot/dshengine.go` 的 `dshBrandSecrets`:名单里已有
   `"DeepSeek"` 与 `"deepseek"` 两条通配,**这两句已被现成的兜底盖住,不需要加名单**;
   补一条回归测试 `TestScrubberCoversRC8ImageErrors` 把这个事实钉住,免得日后有人精简名单。
4. **语义变化,无需改码但要知道**:取消一轮后现在会多出一条 `assistant/message`
   (`interrupted: true`)。`mapper.Map` 会把它映射成一条 `event.Message`,内容是已流出的前缀 ——
   与正常轮的"chunk 流式 + message 收尾"是同一形状,前端无需改。
5. 文档/注释里的 `0.1.0-rc.7` 字样(`CLAUDE.md`、`dsh/README.md`、`internal/config/render.go` 的
   注释样例 + 对应 round-trip 测试、`internal/engine/dsh/protocol.go` 包注释、两个测试里的固定串)。

### 与原执行提示词预判不符的地方(以实际 diff 为准)

- 预判"Session 存储改了 SQLite v2 布局 → resume 与落盘扫描必须复验"——**不适用**:
  我们用 JSONL 持久化,`session-persistence-jsonl` 本次零源码改动。旧会话兼容性风险大幅下降
  (仍按要求实测,见下方回归表)。
- 预判"`HarnessSdkJsonRpcServer` 构造签名/transport 行为可能变"——**没变**,这个最脆的接缝这次是安全的。
- 预判"`dsh-sdk-jsonrpc-demo` 与 agent-teams 有改名动作"——**没改名**,bin 仍是 `lib/bin.js`。
- 预判"品牌 branding 动了不少 → `includeHarnessIdentity` 可能没了"——**仍在**,`system-prompt` 包零源码改动。
- 新发现(原提示词没提):`llm` 的默认重试次数 2→5,以及 rc.8 新增的两条含 `DeepSeek` 字样的

## Step 1 — 升依赖 + 修编译

`dsh/package.json` 22 个 `@deepseek-ai/dsh-*` 锁到 `0.1.0-rc.8`(逐个 `npm view` 核过均已发布)。

**这里踩了一个坑,写下来免得下次再中**:只改 `package.json` 再跑 `pnpm install` 是**不够的**。
直接依赖会升到 rc.8,但传递依赖(尤其被当 peer 解析的那批 —— `dsh-brand`/`dsh-invariants`/
`dsh-attachment`/`dsh-timeout`/`dsh-skill`/`dsh-commands` …)会被 pnpm 判定"已满足"而留在 rc.7:

| | 混装(第一次 install) | 干净重装 |
|---|---|---|
| `pnpm-lock.yaml` 里 rc.7 引用 | 489 处 | **0** |
| `pnpm-lock.yaml` 里 rc.8 引用 | 390 处 | 780 |
| `node_modules/.pnpm` 里 rc.7 包 | 89 个 | **0** |
| `node_modules/.pnpm` 里 rc.8 包 | 23 个 | 63 |

要命的是**混装状态下 `pnpm typecheck` 全绿、`go test ./...` 全绿、发行包也照样出得来** ——
是打包后逐个核对 `package.json` 版本才发现的。dsh 是 developer preview、官方明说 rc 之间会
破坏兼容,这种混合体是定时炸弹。

- **正确做法**:`rm -rf dsh/node_modules dsh/pnpm-lock.yaml && pnpm -C dsh install`。
- **已加闸门**:`scripts/dsh-bundle.sh` 装完闭包后校验 dsh 包版本唯一,不唯一 `exit 1` 并给出修法。
  发行包用的是 `--frozen-lockfile`,所以这道闸门等价于"半吊子 lockfile 别想出包"。

代码改动只有一处:`dsh/plugins/control/index.js` 的 `initialize` 分支加
`await ctx.get('loader')?.await()`(理由见上面"必须改的清单" #1)。
`dsh/plugins/gateway/index.js` 一行没改 —— `resolveAdapterOptions` 会补上 rc.8 新增的必填
`maxRequestImageBytes`,新增的 `resolveAttachments` 是可选的。

编译:`pnpm -C dsh typecheck`、根模块 `go build/vet/test ./...`、`desktop/` 的 `!web` 与
`-tags web` 两套 `go vet`+`go test`、`frontend` 的 `pnpm tsc --noEmit`+`pnpm build`,**全绿**。

### 两条落盘观察(不阻塞升级,但记下来)

`Scrubber` 保的是**流向前端的事件与错误体**,dsh 自己的会话日志是它写它的,不过 Go 的手。
在假网关故意 401 的那轮里,落盘 jsonl 出现:

1. **上游 401 的错误体被原样持久化**进 `assistant/chunk` 的 finish reason 与 `turn/end` 的
   reason(我的假网关故意在错误体里塞满了厂商串,所以扫出 `deepseek-official`/`llm-deepseek`/
   `api.deepseek.com` 各 2 次)。注意这段文字**来自上游网关**,不是客户端泄露自己的配置 ——
   真实部署里那个错误体是 OneCreat 平台网关自己产的,不会带厂商名。
   机制与 rc.7 相同,不是 rc.8 新增。
2. 运行时上下文快照那条 `user/message` 的 **`source.plugin` 元数据**是
   `@deepseek-ai/dsh-system-prompt`。它是事件元数据,不进 `content`(不上行给模型),
   也不进我们的 `projectMessages`(不进前端 History)。

两条都只落在用户自己机器上的会话文件里。要彻底关掉,得让 Go 侧在写 dsh 会话前过一遍
Scrubber(dsh 侧没有这个接缝)或干脆不持久化 turn 错误 —— 都超出本次升级范围。

### 关于 2.4d 的"新建会话后 History 空掉"

**结论:rc.7 时代就有,与本次升级无关,不阻塞。** 做了双版本对照实验:

- 从 `feat/dsh-engine`(rc.7)开 git worktree、装 rc.7 闭包、编出 rc.7 版 `onecreat-web`;
- 同样的操作序列:第一轮 → `History` 有 user+assistant(3 条);
  `NewSession` → 再一轮 → `History` **只剩 system(1 条)**。rc.8 表现完全一致。

根因(静态定位):`internal/boot/dshengine.go` 把 `deps.Session` 这个 `*agent.Session`
**指针**一次性传进 `dsh.Options.Session`,而 `Controller.NewSession()` 走的是
`c.executor.SetSession(agent.NewSession(...))` —— 换的是**新对象**。引擎继续往被弃用的旧
session 写,`ctrl.History()` 读的是新 session,自然空。修法与验收已单独开任务,不混进本次升级。

## Step 4 —(可选)评估 `llm-pi-ai` 替代 `dsh/plugins/gateway`

**结论:不替换,保留我们自己的 `dsh/plugins/gateway`。** 理由两条,都是硬伤:

### 1. 用户可见错误文案带厂商串,而且**指向我们不存在的 UI**

扒了 npm 上 `@deepseek-ai/dsh-llm-pi-ai@0.1.0-rc.8` 的构建产物,`LlmError` 的文案里
`pi-ai` / `llm-pi-ai` 遍地都是,且**不可配置**。最要命的是缺凭证那条 —— 正是执行提示词
Step 4 点名要查的 `MISSING_CREDENTIAL`:

> `llm-pi-ai: no credential for provider route "…"; its profile resolves …, which is not set — store … through the credentials service (**the web Models page writes it**) or export it, and remove apiKeyEnv only if this provider should authenticate from **pi-ai's own environment discovery**`

除了品牌串,它还在教用户"去 web Models 页面填 key" —— 而 OneCreat 的 profile **故意不装**
任何 model selector / 凭证面(见 `dsh/README.md` 红线)。就算把 `pi-ai` 加进 `dshBrandSecrets`
擦掉品牌,擦完剩下的仍是一句把老师引向不存在页面的错误指引,比现在更糟。

对照我们自己的插件,同一场景只会说:
`onecreat-gateway: 缺少凭证,请在环境变量 ONECREAT_DSH_API_KEY 中提供`。

其余同类:`pi-ai model "…" does not support image input`、`pi-ai adapter does not own provider "…"`、
`pi-ai event stream ended without done/error` 等 10 余条。

### 2. baseURL 会退化成**启动期快照**,丢掉会话中途轮换的能力

`llm-pi-ai` 的路由是 `providers` 字典里的静态配置,`baseURL` 是字面量。它 README 说的
"endpoint 改了下次请求就生效"走的是 **user-settings 层** —— 而那个 settings/凭证面正是我们
故意不组合的包。真写成 `baseURL: !!js process.env.…`,那是 profile 加载时求值一次,
往后 `onecreat/credentials.set` 改 env 也不会生效。

我们现在的插件是**每次请求重读 `process.env`**,base URL 与 token 都能中途换(平台 token 约
50 分钟过期,`TestCredentialsRotatedBeforePrompt` 与 `TestGatewayTierAndTokenRotation` 就是钉这条的)。
换成 llm-pi-ai,token 那半靠 `apiKeyEnv` 按请求解析还能保住,base URL 那半会退化。

### 权衡

换掉能省的是我们自己 **78 行**的 gateway 插件(还是全仓库最贴红线的那 78 行),换来的是
不可控的品牌文案 + 一处功能退化。**保留原插件**,`dsh/plugins/gateway/index.js` 本次一行未改
(rc.8 的 `DeepSeekAdapter`/`resolveAdapterOptions` 对我们的用法完全向后兼容)。

日后若要再评估,先看上游有没有把这批 `LlmError` 文案做成可配置。
