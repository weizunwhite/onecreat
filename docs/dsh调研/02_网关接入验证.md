## 2. 让 dsh provider 指向网关:改哪、能否只靠配置

**能只靠配置,不改源码。** dsh 的 `dsh-llm-deepseek` 适配器就是"OpenAI 兼容 chat-completions"客户端,官方 README 明确支持"OpenAI-compatible gateway requests"。两种等价接法:

**接法 A — cordis.yml 里写死(推荐用于我们固定组合的 headless profile)**:
```yaml
- id: llm-deepseek
  name: '@deepseek-ai/dsh-llm-deepseek'
  config:
    baseURL: https://t.weizunxy.com/api/onecreat/v1   # 拼接 /chat/completions => 平台网关端点
    apiKeyEnv: ONECREAT_GATEWAY_TOKEN                  # 只存"环境变量名",不存明文;解析成 Authorization: Bearer
    models: []                                          # 关掉 model catalog 广播(见 §3 漏点②)
```

**接法 B — 纯环境变量(`examples/jsonrpc-agent` 就是这样)**:
- `DEEPSEEK_BASE_URL=https://t.weizunxy.com/api/onecreat/v1`
- `DEEPSEEK_API_KEY=<网关 token>`(或把 `apiKeyEnv` 指到 `ONECREAT_GATEWAY_TOKEN`)

请求头由适配器组装为 `Authorization: Bearer <解析出的 token>` + `Content-Type` + 归因头,POST 到 `${baseURL}/chat/completions`。**这与我们现有网关契约(`POST /api/onecreat/v1/chat/completions`,Bearer token,OpenAI 兼容透传)完全对齐**——平台侧按 tier 映射真实模型、擦除响应里的 `model` 字段、扣点,dsh 侧无需感知。

**wire `model` 怎么填(红线关键)**:`examples/jsonrpc-agent` 里 model "arrives per session over JSON-RPC, so it is not pinned"——即 model 由驱动方经 `initialize`/`session/new` 每会话下发。我们应**下发档位占位符(如 `onecreat` 或 `tier-1`),绝不下发真实 DeepSeek 模型名**;平台网关本就按 token+tier 决定真实模型,占位符即可。这样落日志的 `model` 也是占位符(见 §3 漏点①的缓解)。

**归因头**:适配器会带 `User-Agent`(标识 harness)、`x-deepseek-harness-user-id`、`x-deepseek-harness-session-id`、compaction 请求还带 `x-deepseek-harness-compact: 1`。这些发到网关——**平台网关必须容忍/忽略这些额外头**(不是对用户的泄漏,但是要确认平台不因未知头报错)。这是一条待平台侧确认项。

## 3. 泄漏检查(逐条,源码级)

> 检查对象:Web UI / 终端日志 / session 文件 / 错误响应体。逐条标注严重度与缓解。

| # | 漏点 | 来源 | 严重度 | 缓解 |
|---|---|---|---|---|
| ① | **真实 model + provider 名落进 durable 会话日志** | `SessionEvent` 的 `request/header`(`EpochHeader`,含 provider/model/effort/sampling)与 `request/context`(`provider:string`+`model:string`)是**落盘**事件,且经 `session.event` 通知**全量流给 SDK 客户端**;JSONL(默认 zstd)/SQLite 磁盘文件里都有 | **高** | (a) wire `model` 只下发**档位占位符**,则落盘 model 安全;(b) provider 路由名 `deepseek-official` 仍会落盘 → 需自定义命名适配器或 Go 驱动层过滤;(c) Go 驱动层消费 `session.event` 时,对 `request/header`/`request/context` 做**模型名/provider 兜底擦除**后再喂 `event.Sink`;(d) 若 dsh 独占 session store,**该 store 是本机文件,老师可打开** → 必须保证落盘的是占位符而非真名 |
| ② | **Web UI 的 model selector / settings / 凭证面** | 存在 `ui-model-selection`、`ui-settings-models`、`ui-settings-general`、`credentials-local` 等包;`ctx.llm.listConfigurableProviders()` + catalog(`listModels`)会把 provider `deepseek-official` 与 model 目录暴露到 Web 选择器 | **高(仅当用 dsh Web UI)** | 我们**不用 dsh Web UI**(规划非目标),headless/SDK profile **不组合**这些 UI 包 → 面根本不渲染;并把 `models: []` 关掉 catalog 广播 |
| ③ | **错误/传输异常体里带 baseURL(网关地址)** | `LlmError` 的 TRANSPORT 分支消息:`DeepSeek API request to ${connection.baseURL} failed`;stream 失败同理 | 中(泄的是网关 URL,非模型名) | Go 驱动层对 `agent/error`/error 事件做 URL 脱敏;错误体不含 model 名(错误只带 HTTP status、request-id) |
| ④ | **provider 路由名 `deepseek-official` 硬编码** | `dsh-llm-deepseek` 固定注册该路由名,凡日志/事件/UI 出现 provider 字段即显此名——**直接暴露"底层是 DeepSeek"这一品牌事实**(我们产品连品牌都对用户隐藏) | 中-高 | 要彻底隐藏需**写一个自命名的 OpenAI 兼容适配器插件**(路由名如 `onecreat-gateway`,指向网关),这是**小改动 TS 插件**——意味着"纯配置隐藏 provider"不成立,隐藏品牌需一个薄插件 |
| ⑤ | **compaction 辅助请求头 `x-deepseek-harness-compact: 1`** | 发到网关 | 低 | 平台侧计费可据此区分;非对用户泄漏 |
| ⑥ | **stdout 混入** | SDK/ACP server 都要求 stdout 只走协议帧、日志走 stderr;若组合层误加 console logger 会污染通道 | 低(工程纪律) | profile 不挂 stdout logger |

**运行时实证(2026-08-18,无 key headless 跑)**:`node dsh/lib/bin.js --profile headless "say hi"`(不设 key)→ stderr 报错原文:

```
dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route "deepseek-official";
store DEEPSEEK_API_KEY through the credentials service ... or export DEEPSEEK_API_KEY ...
```

→ **错误体直接泄漏 `deepseek-official`(provider 品牌)、`llm-deepseek`(插件名)、`DEEPSEEK_API_KEY`(env 名)**,三者都暴露"后端是 DeepSeek"。坐实漏点③④是**运行时常态**,Go 驱动层的错误脱敏与自命名适配器不是可选项。(本例未泄漏具体 model id,因 model 是 per-request 解析;但一旦有 key 正常请求,§3 漏点①的 `request/header` 就会带真实 model id。)

**制造错误的泄漏推演(部分已实测,见上;其余基于源码)**:
- 错 token → 网关返 401 → `LlmError('AUTH')`,体里含 HTTP status + request-id,**不含 model 名**;但若 dsh 已记了 `request/header`,该事件里有 model → 走漏点①。
- 错模型名 → 网关按 tier 映射,dsh 下发的是占位符,故此路无真名可漏(前提:我们只下发占位符)。
- 超长输入 → `CONTEXT_WINDOW_EXCEEDED`,体不含 model 名。
- 正常对话 → `request/header`/`request/context`/`assistant/message.usage` 全落日志 → 漏点①是常态泄漏,不是异常态。

## 4. dsh 有没有让用户改模型/API 的 UI

**有**(源码 + **运行时实证**):`packages/client/ui-model-selection`、`ui-settings-models`、`ui-settings-general`、`ui-settings-plugin-inventory`、`credentials/credentials-local`。dsh 官方 Web UI 允许用户切换 model、编辑 settings、录入 API key/凭证。

> **运行时实证(2026-08-18,本机 http://127.0.0.1:3080)**:成功启动 dsh web 后,关掉内测声明弹窗,UI **立即弹出"API 密钥"输入框**(password 输入 + "稍后配置/保存并继续"),用户可直接录入 key;左栏有"设置";会话有"Agent 预设"选择器(标准/PTC/极简/创造模式——这是能力集预设,不直接暴露模型名,但"API 密钥"面是确凿的用户可改凭证入口)。这与"只见档位、隐藏模型/凭证"直接冲突。**这与我们"只见档位不见模型"根本冲突**——正是规划把"走 dsh Web UI + web 插件"列为**非目标**的核心理由。
**将来必须锁死**:任何交付给老师的组合**不得包含**上述 UI 包;若未来真要用 dsh 前端,必须移除/禁用 model-selector 与凭证面,并在网关模式下拦截任何自带 key 的 provider 新增(对齐我们现有 `gatewayActive()` 后端拦截 `SaveProvider/SetModel` 的做法)。

## 5. 结论

**可行,但有 4 处必须堵的漏点(2 高 2 中):**

- ✅ **配置层可行**:`baseURL`+`apiKeyEnv`(仅存环境变量名,不入提交文件)即可让 dsh 走平台网关,契约与现有 `POST /api/onecreat/v1/chat/completions` 对齐,**无需改源码**。
- 🔴 **漏点①(高)**:真实 model/provider 名结构性落进 durable 会话日志且经 `session.event` 流出 → 靠"下发档位占位符 + Go 驱动层擦 `request/header`/`request/context` + dsh store 落盘只存占位符"堵。
- 🔴 **漏点②/④(高/中-高)**:Web UI model-selector/凭证面 + 硬编码 provider 名 `deepseek-official` → 靠"不组合 dsh Web UI 包 + 写自命名薄适配器插件隐藏品牌"堵;**注意:彻底隐藏 provider 品牌需一个小 TS 插件,不是纯配置**。
- 🟡 **漏点③(中)**:错误体带网关 URL → Go 驱动层脱敏。
- ⚠️ **待平台侧确认**:网关能否容忍 dsh 的归因头(`User-Agent`/`x-deepseek-harness-*`);网关是否接受 wire `model` 为占位符并正确按 tier 映射。

**一句话**:网关**可行但有可堵的漏点**,且其中"隐藏 provider 品牌名"这一条无法纯配置完成、需一个薄适配器插件——比规划文档 Phase 2.3 只写"Go 驱动层兜底过滤"要多一件事。
