## 1. Agent loop 结构(turn / step 模型)

dsh 的核心循环是**事件溯源**的,不是我们那种"stream→执行工具→再 stream"的命令式循环,而是一棵 Cordis 插件树对一条**只追加(append-only)的 `SessionEvent` 日志**发事件:

```
turn/start
  ├─ 认领 next-step 输入 + 一条排队消息
  ├─ 组装 prompt sections + tool schemas
  ├─ agent/pre-step        (瀑布式,可 reject / 改写消息)   ← 系统提示注入点
  │   step/start
  │   ├─ 追加进入的消息为 user/message
  │   ├─ 从日志派生模型历史 deriveMessages()
  │   ├─ agent/request → llm/stream → assistant/chunk* → assistant/message   ← provider 接缝
  │   ├─ tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  │   step/end
  │   └─ 工具还欠一次请求 / 新输入到达 → 认领 → 下一 step
  └─ agent/turn-stopping   (串行,无 next())
turn/end
```

- **step** = 一次模型请求 + 它调用的工具;**turn** = 0 个或多个 step。
- `agent/pre-step`、`agent/request`、`llm/stream`、三个 `tools/*` 都是**瀑布(waterfall)**,监听器必须调 `next()` 才往下传——这就是插入策略/钩子而不改核心的机制。
- **模型可见 = 必落日志**(runtime invariant):任何进入模型请求的东西都必须能从日志重建。新的模型可见输入必须新增一个 SessionEvent 类型。

对照我们内核:`internal/agent.Agent` 的 run loop ≈ dsh 的 `core/agent-loop`;我们的 `Session.Messages` ≈ dsh 的 `core/session` 事件日志(但 dsh 是纯事件溯源、消息历史是**派生**的,我们是直接存消息)。

## 2. 文档化的扩展点清单

Cordis 的口号是"没有可打补丁的特权核心",全部能力通过在 `ctx` 上挂服务/监听事件扩展。三类事件:

| 类别 | 事件 | 用途 |
|---|---|---|
| **Session 事件**(durable,落日志,经 `session/event` 广播) | `turn/*` `step/*` `user/message` `assistant/chunk` `assistant/message` `tool/call` `tool/result` `todo/write` `request/header` `request/context` `plan/mode` `compaction/*` `hook/invoked` `hook/result` … | 需要"重载后仍在"的事实 |
| **Agent 事件**(`agent/*`,带活的 Agent 句柄) | `agent/pre-step` `agent/request` `agent/turn-stopping` `agent/inbox/*` `agent/error` … | 观察/拦截在飞的工作 |
| **Capability 事件**(把策略/适配器挂到接缝) | `fs/*` `tools/*` `telemetry/*` | 不 import 循环就能加策略 |

新增行为的落点(官方"Where new behavior goes"表精选):

| 目标 | 机制 | 与我们的对应 |
|---|---|---|
| 加模型 provider | 在 `ctx.llm` 注册 adapter | ≈ `internal/provider` 注册表 |
| 加模型可见工具 | 在 `ctx.tools` 注册,schema 自动进 prompt | ≈ `internal/tool` 注册表 |
| 加 shell 执行 | 注册 `ctx.shell` 后端(local 走 `ctx.subprocess`) | ≈ 我们的 bash 工具 |
| **拦截请求/工具/turn** | 用其 `agent/*` 或 `tools/*` 事件 | **证据引擎接入点** |
| 加模型可见上下文 | `agent.inject()`,落到下一次被采纳的请求 | ≈ 我们的 memory/coaching 注入 |
| 加人类命令 | 注册 `ctx.commands`,不经模型 turn 直接派发 | ≈ 我们的 `/slash` |
| 加后台工作 | 注册 `ctx.jobs`,`job_*` 工具收集/停止 | ≈ 我们的 Jobs |
| fork 活会话 | `ctx.sessions.fork(source, boundary?, childId?)` | ≈ 我们的 Fork/Branch |
| 生成会话标题 | 注册唯一 `ctx.sessionTitle` provider | ≈ 我们的 Label |
| 管理同会话目标 | `ctx.goals` | (我们无直接对应) |

**证据引擎接入点(关键)**:工具执行管线暴露 `tools/pre-execute` / `tools/post-execute` 两个瀑布钩子 + 落日志的 `tool/result` / `todo/write` / `hook/invoked` / `hook/result` 事件。我们现有 `internal/evidence`(匹配 `complete_step`↔`todo_write`、累积证据链)可以**订阅这条事件流**而不必重写成 TS 插件——正是规划 Phase 2.2 设想的"Go 驱动层消费 dsh 工具事件流喂现有 evidence"。这条路已从源码证实可行。

## 3. 嵌入方式(决定"Go 拉起子进程驱动"可行性)

dsh 提供**两条 stdio 协议**可被外部进程驱动,外加一个一次性 headless runner。三者能力**互补但都不完整**:

### 3a. SDK JSON-RPC over stdio(`packages/sdk/server` = `dsh-sdk-jsonrpc-server`)
- **newline-delimited JSON-RPC 2.0**,一帧一行,`stdout 只走协议帧、诊断必须走 stderr`。
- 传输类 `JsonRpcLineTransport` 在 `packages/sdk/protocol`,TS client(`dsh-sdk-client`)与 Python SDK 共用同一 wire。
- 方法:
  - client→server:`initialize`(带 cwd + provider/model 路由 + 可选 maxTokens)、`session/prompt`(排队一条 user message,**立即返回 messageId**)、`shutdown`。
  - server→client 通知:`session.event`(**运行时每一条 durable 事实,全量、不过滤**)、`session.status`(整 agent running/idle)、`subagent.started`、`subagent.finished`。
- **能力缺口(预览期)**:
  1. **无 mid-turn cancel** —— wire 上没有取消方法,放弃一个 turn 只能**关闭子进程**。
  2. **审批 = dead capability** —— 传输支持 server→client 请求,但 server **从不发**;"responder surface 为将来审批流预留"。即 JSON-RPC 路径下**审批未实现**。
  3. **无 per-prompt result** —— messageId 只标识入队,客户端要自己界定"活动区间"(从 messageId 出现到下一次整体 idle)。
  4. **无 per-session close**;SDK 建的 agent 一直活到进程 shutdown。
  5. adapter 自动挂载**只认 DeepSeek**:`initialize` 对未拥有的 `deepseek-official` 路由自动挂 `dsh-llm-deepseek`,其它未拥有 provider 直接初始化失败。
- **优点**:事件保真度最高(chunk 级流式、工具起止、usage、plan、todo 全都流出),正对我们 `event.Sink` 的渲染需求。
- **现成蓝本**:`examples/jsonrpc-agent/cordis.yml`(无人值守 coding agent 组合)+ `keyless-smoke.e2e.ts`(**用 mock LLM 无 key 冒烟**)。

### 3b. ACP over stdio(`packages/acp/acp` = `dsh-acp`)
- **Agent Client Protocol**(agentclientprotocol.com)的 JSON-RPC stdio server,"automation-only"。
- 方法:`initialize` / `session/new`(仅新会话,cwd)/ `session/prompt` / `session/cancel` / `session/update` / **`session/request_permission`**。
- **相对 SDK 的优势**:**有 cancel**(`session/cancel`)、**有审批**(`session/request_permission` 一次性 allow/reject,带 tool call id,客户端可自动答)。
- **严重限制**:
  1. **只推 committed 消息** —— `session/update` 只在 `assistant/message` 提交时发 chunk,**无 token 级流式、无 reasoning、无工具活动、无 plan、无 title、无 usage**(全部留在日志里,不上 wire)。这对我们的桌面实时流式 UX 是**明显降级**。
  2. **仅新会话** —— load / list / **resume** / delete / **fork** 全不支持。
  3. **协议层拒绝 mcpServers** —— `session/new` 传非空 `mcpServers` 直接 reject(MCP 必须在 cordis.yml 组合层挂,不能经协议传)。
  4. 不暴露 editor 导航、transcript replay、commands、**modes**、plans、titles、tool presentation。

### 3c. headless 一次性(`packages/bundle/headless`)
- `dsh --profile headless "task"`:建一个 fresh agent、把 task 当普通 user message 提交、等静默、把最后一条非空 assistant 文本写 stdout、退出(成功 0 / 否则 1)。**不开任何监听端口**、无交互后续。适合"跑一道题打个分",不适合做常驻可驱动引擎。

### 嵌入可行性结论
- "Go 进程拉起 dsh 子进程并用 stdio JSON-RPC 驱动"**技术上成立**,官方就是这么给 Python/TS SDK 和 subagent 后端用的(`dsh-subagent-dsh-sdk`、`dsh-subagent-acp` 就是内部消费者)。
- 但**没有单一协议覆盖我们 Controller 全貌**:SDK JSON-RPC 流式保真但缺 cancel/审批;ACP 有 cancel/审批但流式/resume/fork 残废。Phase 1 需要在两者间做取舍或组合(见 05 节映射表与 04 结论)。

## 4. Session 存储(格式 / 位置 / fork / 外部可读性)

- 内存态:`Session` = append-only `SessionEvent` 日志,**消息历史是 `deriveMessages()` 派生的,不单独存**;replay = 重新派生。
- 落盘(持久化接缝 `ctx.sessionPersistence`,两后端可换):
  - **JSONL**(`dsh-session-persistence-jsonl`):每会话一个文件,默认 **zstd 压缩帧**(可配 `compression: none` 出原始行),原子写、崩溃恢复(把中断的 turn 补 `turn/end{interrupted}`)。`locate()` 返回该会话文件的绝对路径。
  - **SQLite**(`dsh-session-persistence-sqlite`):`node:sqlite`,一事件一行 `(session_id, seq, type, time, data, …)`,所有会话共享一个 DB,`locate()` 返回 undefined。
- **格式有版本号**(`SESSION_FORMAT_VERSION`),加载时**拒绝其它版本**(无迁移路径,只报升级方向)。
- **fork / summary**:fork 由 `ctx.sessions.fork()` 一等支持;摘要/压缩由 compaction 接缝(`compaction/start|summary|end` 事件)提供。
- **外部程序能否安全读**:JSONL 默认 zstd 压缩(需解压)、SQLite 是标准库;官方文档警告 `SessionLocation.path` 是"位置提示,不是授权/新鲜度保证"。生态里确有 dual-writer 损坏史 → **谁是会话真源必须单一化**(见规划 Phase 1.6)。因两后端格式/位置都与我们 Go 会话文件不同,`engine=dsh` 时让 dsh 独占其 store、我们 Go 侧不写会话文件,可干净切分,避免双写。

## 5. Provider 层(是否只有 DeepSeek?base URL / header 可配?)

- **不是只有 DeepSeek**,但**内置就 DeepSeek 一族**:
  - `llm/llm-deepseek`(`dsh-llm-deepseek`):直接 fetch + SSE,拥有路由名 **`deepseek-official`**(硬编码,重复注册抛 `DUPLICATE_ADAPTER`)。
  - `llm/llm-pi-ai`(`dsh-llm-pi-ai`):同一接缝的第二实现,catalog 名 `deepseek`,库支持多 provider(pi-ai 生态)。
  - `llm/llm-retry`、`llm/token-meter` 是横切。
- **base URL / header 完全可配(网关关键,详见 02)**:`dsh-llm-deepseek` 的 config 支持 `baseURL`(默认 `https://api.deepseek.com`,或环境变量 `$DEEPSEEK_BASE_URL`,请求时拼 `/chat/completions`)、`apiKeyEnv`(默认 `DEEPSEEK_API_KEY`,**只存环境变量名、绝不存明文 key**,解析成 `Authorization: Bearer`)。README 明写支持 "OpenAI-compatible gateway requests"。**指向平台网关是纯配置,不改源码。**
- **⚠️ 泄漏隐患(详见 02/00)**:`request/header`(EpochHeader,注释原文"provider, model, reasoning effort, sampling")与 `request/context`(`provider:string` + `model:string`)是**落盘 + 经 `session.event` 流出**的 durable 事件——真实 provider(`deepseek-official`)与真实 model id 会结构性地进会话日志。

## 6. 与我们现有概念的映射表(Controller 方法 ↔ dsh 能力)

我们 `internal/control` 导出约 70 个方法;下表覆盖规划点名的核心集。"SDK"=JSON-RPC 路径,"ACP"=ACP 路径,"组合层"=cordis.yml/服务直驱(非 wire)。

| 我们的 Controller 方法 | dsh 对应 | SDK | ACP | 说明 |
|---|---|---|---|---|
| `Submit` / `Send` / `Run` | `session/prompt` | ✅ | ✅ | 排队一条 user message |
| `Cancel` | ACP `session/cancel` / SDK 无 | ❌(杀进程) | ✅ | **SDK 路径无 wire 取消** |
| `Running` | `session.status`(running/idle) | ✅ | 部分 | agent 级空闲判定 |
| `Approve` / `PendingApprovals` / `EnableInteractiveApproval` | ACP `session/request_permission` / `ctx.approval` | ❌(dead) | ✅ | **SDK 审批未实现**;组合层可用策略自动批 |
| `SetPlanMode` / `PlanMode` | `dsh-plan-mode`(`/plan` 命令 / `ctx.planMode.set`) | ⚠️ | ❌ | **两 wire 都不直接驱动 modes**;需命令面或注入 |
| `History` | `session.event` 流 / 持久化 load | ✅ | ❌ | ACP 无 replay |
| `NewSession` | `session/new`(ACP)/ `initialize` 新 sessionId(SDK) | ✅ | ✅ | |
| `Resume` | 持久化 `prepare/load(id)` | ⚠️(组合层) | ❌ | ACP 明确不支持 resume |
| `Fork` / `ForkNamed` / `Branch` / `SwitchBranch` | `ctx.sessions.fork()` | ⚠️(组合层) | ❌ | 非 wire 一等能力 |
| `Compact` / `SummarizeFrom/UpTo` / `CompactRatio` | compaction 接缝 | 事件可见 | ❌ | `compaction/*` |
| `Rewind` / `Checkpoints` / `InvalidateCheckpoints` | 无直接对应(dsh 无文件级 checkpoint) | — | — | **我们的 `internal/checkpoint` 需保留 Go 实现** |
| `AddMCPServer` / `ConnectMCPServer` / `ConfiguredMCPNames`… | `dsh-mcp-client`(每 server 一实例) | 组合层 | ❌(协议拒绝) | 见 §7 |
| `Skills` / `RunSkill` / `CustomCommand` / `Commands` | `packages/skill/*` + `ctx.commands` | 组合层 | ❌ | `/skill` 有对应 |
| `Memory` / `QueueMemory` / `ForgetMemory` | `agent.inject()` + 自定义 | 需自建 | — | 无内置记忆库,靠注入 |
| `Balance` / `LastUsage` / `SessionCache` | `assistant/message.usage` / token-meter | ✅ | ❌ | 点数计费仍在我们 Go+平台侧 |
| `SetCoachMode` / `SystemPrompt` / `Compose` | `agent/pre-step` 注入 + 系统提示接缝 | 组合层 | 组合层 | 教练人设注入点 |

**读表结论**:我们 Controller 的"最小子集"(Submit/Send/Cancel/Running/Approve/PendingApprovals/SetPlanMode/History/NewSession/Resume/SessionPath)里,**Cancel、Approve/PendingApprovals、SetPlanMode、Resume 四项在单一 wire 上都有缺口**——这是 Phase 1 侵入式工作量的真实来源,规划文档未充分点出(见 04)。

## 7. MCP 接入方式(硬件 MCP 能否零改动接?)

- `packages/mcp/mcp-client`(`dsh-mcp-client`):cordis.yml 里**每个 MCP server 挂一个实例**,支持 `transport: stdio`(command/args/env/cwd)与 `streamable-http`(url/headers)。
- 工具名格式 **`mcp__<serverName>__<rawName>`** —— 与我们内核、Claude Code、Codex **完全同形**。
- 因此 `bin/onecreat-hardware-mcp`(stdio 二进制)**零改动可挂**:

```yaml
- id: mcp-hardware
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    serverName: hardware        # 工具变成 mcp__hardware__<tool>
    transport: stdio
    command: /abs/path/bin/onecreat-hardware-mcp
```

- ⚠️ 注意:ACP 路径协议层**拒绝**经 `session/new` 传 mcpServers,所以 MCP 只能走**组合层(cordis.yml)**注入——对我们无碍(本就该在 profile 里固定组合硬件 MCP)。
