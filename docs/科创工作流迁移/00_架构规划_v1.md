## 0. 摘要

1. **定位**:OneCreat = 零一优创的「科创项目操作系统」——把 NASApp 里那条跨四台机器的科创工作流,收成一个本地单体。
2. **形态**:Go 单二进制 `onecreat-web` 起本地服务 + 浏览器当 UI(已有 Web 模式,主分发形态);**不做桌面 App 壳**。
3. **决策一(架构)**:科创工作流是**应用策略**,只长在 `control.Controller` 之上;绝不碰 `engine.TurnEngine` 接缝,绝不给 Controller 加锁。
4. **决策二(数据)**:**文件位置即状态,项目目录即真源**——原地接管 `/Users/localwork/课题/01_在研项目/P26X-NNN_短名/`,OneCreat 不搬数据、不建第二真源。
5. **决策三(交互)**:**业务决策点 ≠ 安全审批**——新建「决策收件箱」,与 `approvalBroker` 并列,**YOLO/bypass 不能跳过**。
6. **引擎**:dsh 默认、native 兜底、pi 新增为可选;三者都必须过同一条 `toolpolicy.Pipeline.Before`,`boot.requireToolGating` fail-closed。
7. **商业化**:现在**只定义接口、不实现**(feature key `workflow`、`AccountSession` 主体字段、`billing.ReportOutcome`、平台影子表)。
8. **路线**:M0 拍板 → M1 领域内核 → M2 一键材料 → M3 对话型+决策收件箱 → M4 工作台 UI → M5 数据切换;引擎线 E 并行,商业化线 C 后置。
9. **下一步(M0)**:老板拍 5 个产品边界问题([§9](#9-m0-待拍板的-5-个产品边界问题)),同时把注册表收口到 v17 并加机械守卫。 **M0 五问已于 2026-08-23 拍板([`01_M0决策记录.md`](01_M0决策记录.md))。**
10. **对 pi 的建议**:先做 P0+P1(5–7 人日)拿到能过门禁 e2e 的 spike,与 dsh 做一次真实对照,**再决定是否长期双养**。

## 1. 背景与目标

### 1.1 NASApp 的「科创工作流」是什么

不是一个模块,而是一条**跨 4 个物理位置、由一份 JSON 注册表定义、由 40+ 个 skill 执行、以文件位置为状态机**的流水线(报告 01 §0)。

| 物理位置 | 角色 | 关键资产 |
|---|---|---|
| 老板的 Mac | **文件真源** | `课题/00_产题评题/`、`课题/01_在研项目/P26X-NNN_短名/`、`99_工作区/scripts/`、`mac-agent/macfs_agent.py:8787` |
| QNAP NAS `192.168.6.131` | 仓库 + 柜台 | `web/main.py`(FastAPI 单文件 **16939 行**)、`00_项目总库/` 镜像、`topic_index.json`、`.kanban.json`、**`project_codes.json`(发号唯一权威)** |
| M2 Mac mini `192.168.6.158` | 大脑 / 车间 | `brain/`(`workflow_registry.json` + `pipeline.ts` + `engine.ts` + `server.ts`)、pi-daemon |
| 教师平台 `t.weizunxy.com` | 授课交付 / 结题 | Supabase、项目包上传(写凭证只在 iOS Keychain) |

方法论资产实际上只集中在**三处**(报告 01 §0):
- `brain/registry/workflow_registry.json`(69 行)—— 阶段与材料的**机器契约**;
- `/Users/zunwei/code/oneup-skills/` 的 40+ 份 `SKILL.md` —— **方法论正文**;
- 两份人读正本 README(`00_产题评题/README.md` v16、`01_在研项目/README.md`)—— 状态机与七目录判例表。

其余绝大部分代码是把这三处粘到 NAS/iOS/Mac 上的**胶水**。报告 01 §6.1 的判断:**可平移的"方法论内核"约占价值的 80%、代码量的 10%。**

### 1.2 为什么迁

| 动因 | 事实依据 |
|---|---|
| 三端物理拓扑本身就是成本 | Mac↔NAS↔mini 靠 rsync/ingest/软链拉齐,还得写防回环规则(`App产物/` 单向,报告 01 §2.3) |
| 多端一致性反复漂移 | 组别枚举写了 3 份;十流程 vs C 板十一列不同源;`WorkflowMapView.swift` 的 LV.1/LV.8 文案已过期(报告 01 §1.5 / §6.4④) |
| 远程受控执行链没有存在理由 | OneCreat 跑在本机,自带 `toolpolicy` 门禁与 permission gate,`macfs_agent.py` 那条 "手机→NAS→Mac 白名单执行" 整条可以消失(报告 01 §6.2) |
| 证据引擎正好对上 | OneCreat 的 `internal/evidence` 与 NASApp 的 `evidence_ledger` 是**两套独立发明的同一个想法**,迁移是合并它们的最好时机(报告 01 §6.5) |
| 作用域模型正好对上 | `internal/runtime` 的 Process→Workspace→Session→Turn 恰好能表达"一个项目共享的服务 vs 一个材料任务私有的东西",比 NASApp 的目录约定 + 全局并发闸(默认 2)粒度细得多(报告 01 §6.5) |

### 1.3 迁成什么样

- **形态**:`onecreat-web` 单二进制起本地 HTTP 服务 + 浏览器 UI(`make build-web` / `make release-web`,见 `docs/Web模式.md`),与 dsh 的 `dsh web` 同形态。**不做桌面 App 壳。**
- **范围**:先内部用(创始人 + 自家老师),架构上预留外部商业化(按机构/老师/学生分权、按档位与产出物计费)。
- **离线**:方法论正文(skill / 注册表 / 知识库)**随发行包内置**,只有身份与计量走网,断网能干活(报告 02 §4.3 缺口 6:老师在教室常无稳定网络)。

### 1.4 与《平台重构蓝图》的关系

`docs/平台重构蓝图.md` 的核心判断是 **"不重写引擎,翻面前台 + 做减法"**,并给出三条设计铁律,其中第 2 条是 **"绝不一个垂直一个定制面板"**。

本规划是这条思路在科创工作流上的**具体化**,不冲突:

| 蓝图条目 | 本规划的对应 |
|---|---|
| Phase 1 ✅ 首页启动台 | 沿用。`Welcome.tsx` 的 7 张卡增加一张 `workflow` 入口卡 |
| Phase 2 ❌ 抽 `WorkflowSurface` | **本规划不依赖它**。科创工作台是新建的 `mainView="workflow"`,`HardwarePanel.tsx`(1459 行)保持原样 |
| Phase 3 ❌ skill 元数据驱动启动台 | 本规划的注册表(`workflow_registry.json` 内嵌)是更强的版本:它不只有 category,还有 stage/deps/outputs/platform.file_type |
| Phase 4 ❌ CoWork 编排 | 本规划的 M2「一键材料流水线」**就是** Phase 4 的落地形态(拓扑排序 + 依赖注入 + 质量四件套),但走 Go 领域服务而不是编排 skill |

**关于铁律 2 的自查**(报告 02 §5.6 明确要求做这一步):科创工作台需要"阶段推进按钮 / 立项-未立项决断 / 材料 DAG 齐备度 / 证据补齐清单 / 准则 confirm"这类**非对话交互**——与硬件面板"编译/烧录/串口"按钮同类,**定制面板成立**。

## 2. 设计铁律(八条,全部继承自现有架构守卫)

> 这八条不是新造的纪律,每一条都对应仓库里一个**已经在跑的机械守卫**。左列写守卫,右列写迁移含义。

### 铁律 1 · 科创工作流是应用策略,只长在 `control.Controller` 之上

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `internal/engine/boundary_test.go`:`TestTurnEngineStaysMinimal`(`TurnEngine` 只能有 `Start`)、`TestTurnHandleStaysMinimal`(只能有 `Cancel`/`Wait`)、`TestEngineInterfacesRejectApplicationPolicy`(14 个禁用动词:`Approve PendingApprovals History Resume Fork Rewind Plan SetPlanMode NewSession SessionPath Compact Branch Submit Send`)、`TestEngineBoundaryDependsOnNoPolicy` / `TestDSHAdapterIsNotASecondCore`(禁 import `control/toolpolicy/permission/checkpoint/evidence/memory/billing/hook/skill/tool/plugin`,`internal/engine` 连 `internal/agent` 都不许) | 任何"阶段/课题/材料"概念**不许**出现在 `TurnEngine` 上;新建的 `internal/project`/`workflow`/`topic`/`numbering` 四个包**不得**被 `internal/engine*`、`internal/agent` import,否则守卫红 |

### 铁律 2 · 阶段/课题/项目状态不上 Controller、不上 turnState

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `internal/control/facade_test.go`:`TestControllerHoldsNoDomainLock`(AST 扫 `type Controller struct`,字段必须在白名单里,**且不得出现任何 `sync.*` 字段**)、`TestControllerFileStaysAFacade`(`controller.go ≤ 950 行`,当前 888 行)。`desktop/app_facade_test.go`:`TestAppHoldsNoDomainState`(字段白名单 + 无锁)、`TestAppFileStaysAFacade`(`app.go ≤ 900 行`,当前 793 行)、`TestAppMethodsAreThin`(方法体 ≤ 26 行) | 工作流领域状态放**新服务**(自己持锁),Controller 至多持一个句柄;加句柄要显式把字段名加进 `facade_test.go` 的 `allowed` 白名单——这是一次**有审计痕迹的决定**,正是守卫的用意。`controller.go` 只剩 62 行余量,`app.go` 只剩 107 行余量,**新代码基本不能往这两个文件里写** |

### 铁律 3 · 门禁走 `toolpolicy.Pipeline`,fail-closed,无配置开关可绕

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `internal/toolpolicy/policy.go` 的 `Pipeline.Before` 已发布阶段顺序:**plan mode 只读门 → `Gate.Check`(交互式审批阻塞在这里)→ `Hooks.PreToolUse`(exit 2 = 拒绝)→ PreEdit 检查点快照 → context 注入(evidence→jobs→memory)**。快照**刻意排最后**:被拒绝的调用不该留下一个"根本没发生的改动"的回退点。`internal/agent/policy_boundary_test.go`:`TestEngineDoesNotImportProductPolicy`、`TestExecuteOneIsThin`(`executeOne ≤ 55 行`)。`internal/boot/engine.go` 的 `requireToolGating`:引擎必须声明 `CapHostedTools \|\| CapGatedTools`,否则装配期返回 `engine.UnsupportedError` | 如果科创工作流要加"阶段门"(例:未完成阶段三签署不许进阶段五),它是 `Pipeline` 的一个**新阶段**,不是 `agent` 循环里的 `if`。这样 native 走 `agent.Agent`、dsh 走 `boot.dshDecider`、pi 走 `boot.piDecider`,**三条路自动同样受管**。⚠️ 一处限定见 [§10-R4](#10-风险与未决) |

### 铁律 4 · 注册表唯一真源,未注册类型 fail-closed

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| NASApp 侧:`workflow-registry.ts:67-83` 启动即校验(重复/未知阶段直接抛)、`materials.ts:10` 的 `resolveSkill()` 返 null → `pipeline.ts:263-277` 记「未知材料类型」。OneCreat 侧的同款文化:`internal/config` 的 `TestRenderTOMLRoundTrips`、`internal/eventwire` 的 `TestKindNamesCoversEveryDeclaredKind`、`TestKindWireNamesAreStable` | 阶段/材料/skill/依赖/输出/平台 `file_type` 全在一份 `workflow_registry.json`,**内嵌进二进制**(`go:embed`),启动即校验。组别/来源/十流程等枚举**只定义一次**并加机械守卫(枚举覆盖测试 + JSON round-trip),杜绝 NASApp 的三份漂移(报告 01 §2.1②:组别枚举写了 3 份) |

### 铁律 5 · 文件位置即状态,项目目录即真源

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `00_产题评题/README.md` v16 拍板:题的状态由它在哪个目录决定,`topic_index.json` 只是扫描产物。OneCreat 侧同构先例:硬件证据链落 `<workspace>/tests/hardware_evidence.jsonl`(报告 02 §1.5 / §6.1);`internal/workspace.Context` 不可变、始终绝对、**运行期切 workspace 绝不 `os.Chdir`** | 项目实体**原地接管** `课题/01_在研项目/P26X-NNN_短名/`(七目录 + `project.json`),OneCreat 不搬数据、不建第二真源;项目级运行状态用 **append-only `.onecreat/workflow.jsonl`**(与 `hardware_evidence.jsonl` 同构)。理由:证据必须和它证明的东西住在一起,才能随项目一起备份/交付/归档(报告 02 §6.4(3)) |

### 铁律 6 · 业务决策点 ≠ 安全审批

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| OneCreat 的 `approvalBroker`(`internal/control/approval.go`)语义是"**要不要允许这个工具跑**",并且带 YOLO/bypass;NASApp 的确认卡语义是"**任务已经跑完了,你要不要接受这个业务结论**"(报告 01 §6.4③)。至少 5 个地方"必须老板亲手点":立项建档、未立项判定(必填 reason)、产题准则 confirm、引擎档位选择、P 卡拨段位 | 新建**决策收件箱(Decision Inbox)**,与 `approvalBroker` **并列、语义独立**;**YOLO/bypass 不能跳过**。硬套 `toolpolicy` 会把两件事混起来,而且会被 bypass 掉——那是产品事故 |

### 铁律 7 · 引擎按"新会话"选择,`Record.Engine` write-once

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `internal/session/session.go`:`Record{ID, Engine, Store, Workspace, Title, Ephemeral, Kind, …}`,**`Workspace` 与 `Kind` 写一次不可改**;`Store` 是引擎的转录引用,registry 从不解析。报告 03 §6.2 的四条理由:转录真源不同、`Store` 的解读方式由 `Engine` 决定、`cpBound` 按 native 日志建立、`enginePersistsTranscript` 决定要不要写转录文本 | 新建会话/标签时选引擎 → 存进 `Record.Engine` → **该会话终身不变**;打开历史会话按 `Record.Engine` 装配;**会话中途换引擎硬拒**。全局配置只做默认值(`flag > ONECREAT_ENGINE > cfg.Engine > "native"`,未知名字**报错不静默回退**) |

### 铁律 8 · SaaS 红线不变

| 来自哪个守卫/事实 | 迁移含义 |
|---|---|
| `config.ModelPrivacyPolicy` 由 `boot.Build` **无条件**追加到系统提示(即使用户自定义 `system_prompt`);dsh 侧三道防线:`mapper.go` 丢弃 `request/header` + `request/context`、`Scrubber` 兜底替换、`wireModel()` 下发档位名 `tier-N`;`internal/account/boundary_test.go` 的 `TestNothingElseReadsTheAccountEnvironment` **全树扫描**,任何非测试源码读写 `ONECREAT_GATEWAY_URL/_TOKEN/ONECREAT_TIER` 就红 | 真实模型名不得出现在 UI / 日志 / 事件流 / 错误体。工作流事件(`workflow.material_done` 之类)与产物文件同样受此约束——**产物里也不许出现模型名**。方法论正文随发行包内置,只有身份与计量走网 |

### 3.2 L4 领域层:四个新包的职责与边界

| 包 | 职责 | 作用域挂点 | 不许做的事 |
|---|---|---|---|
| `internal/project` | 项目实体:P26 身份、七目录判例(`bucket.Classify(materialType, relpath)`)、`stage`、`project.json` 读写、`workflow.jsonl` append | **workspace scope**(由 `boot.Factory.OpenWorkspace` 创建,与 LSP/CodeGraph 同级,refcount 到 0 才释放) | 不搬目录、不改名(换业务线走外部 `reline_project.py`);不把项目做成"全局 store 里的一条记录 + 目录指针"(目录一搬就烂,报告 02 §6.4(6)) |
| `internal/workflow` | 注册表 loader(内嵌 + 启动即校验)、材料 DAG / 拓扑排序 / 依赖检查 / 依赖注入、材料作业编排、质量四件套、对话线程状态机、决策收件箱 | session scope(作业)+ workspace scope(线程持久化) | 不 import `internal/engine*`;不在这里做 skill 执行(那是 `internal/skill` + Controller 的活) |

## 6. 双引擎与门禁

### 6.1 引擎选择的产品形态

- **新建会话/标签时选引擎**(dsh 默认 / pi / native)→ 存进 `Record.Engine` → **该会话终身不变**;
- 历史会话按 `Record.Engine` 装配;
- 状态栏显示引擎名与**能力表**;
- `compact` / 会话 rewind / branch 在 dsh、pi 下**按能力禁用并给人话原因**(后端仍独立校验——UI 不是安全边界)。

**为什么不能中途换**(四条,全部有代码支撑):① 转录真源不同(native 是 `agent.Session`,dsh/pi 在 sidecar 侧);② `Store` 字段怎么解读由 `Engine` 决定;③ `cpBound`(turn→消息索引)按 native 日志建立,换引擎全失效;④ `enginePersistsTranscript` 决定要不要写转录文本,中途改会产生半真半假的文件。

⚠️ **`Record.Engine` 现在没有 write-once 校验**——`internal/session/session.go` 只有 `EngineNative = "native"` 一个常量,`Workspace`/`Kind` 有 write-once 语义而 `Engine` 没有。落 pi 时**顺手补上**。

### 6.2 pi 适配器 `internal/engine/pi` 设计要点

| 要点 | 内容 | 可复用度(相对 dsh) |
|---|---|---|
| 进程拉起 | 复用 dsh `runtime.go` 的三级查找(配置 > 主程序旁 `runtime/pi` > 从 cwd 向上找),改目录名 | ~80% |
| 传输 | **JSONL,严格按 `\n` 切**。pi 不是 JSON-RPC 2.0:命令是扁平 `{"id","type",…}`,响应 `{"id","type":"response","command","success","data"}`,事件一般不带 id。Go 侧 `bufio.Scanner` 天然只按 `\n` 切(避开了 Node `readline` 会在 `U+2028/2029` 上错切的坑),buffer 照抄 dsh 的 16MB 上限 | ~60% |
| 一轮收敛 | `prompt` → … → `agent_settled`(相当于 dsh 的 `session.status: idle`) | — |
| 事件映射 | **不新增 `event.Kind`**:`turn_start`→`TurnStarted`;`text_delta`→`Text`;`thinking_delta`→`Reasoning`;`message_end`→`Message`+`Usage`;`tool_execution_start`→`ToolDispatch`;`tool_execution_end`→`ToolResult`;`extension_error`/`auto_retry_*`→`Notice` | 0%(重写),但**结构照抄**(纯函数 + 单测) |
| **门禁通道** | `pi/extensions/onecreat-gate.ts`:`tool_call` 钩子(**async + 可 block + 错误即拦截**)+ `ctx.ui.input({title:"__onecreat_gate__"})` 走官方 **extension UI 子协议**阻塞等 Go 裁定;`undefined` = **deny**(唯一要靠我们纪律的一处,必须显式写) | 见 §6.3 |
| `complete_step` 工具桥 | `pi.registerTool({name:"complete_step",…})`,`execute` 里同样用 extension UI 子协议把参数送回 Go(证据引擎是它的裁判) | — |
| 网关 | provider 名固定 `onecreat-gateway`、model id 固定 `tier-N`;`models: []` 关目录广播;**`registerProvider` 的 async `resolve()` 回调每次请求取 token** —— 这正好解决"平台 token 约 50 分钟过期、子进程 env 是 spawn 快照"(dsh 靠自补 `onecreat/credentials.set` 解决) | — |
| 隔离 | `--no-extensions --no-skills --no-context-files -na` + 独立 `PI_CODING_AGENT_DIR` + `PI_OFFLINE=1` + `PI_TELEMETRY=0` + env 白名单。**明确不信任项目本地 `.pi/`**(学生项目里放 `.pi/extensions/` = 任意代码执行) | — |
| e2e | `ONECREAT_PI_E2E=1 go test ./internal/engine/pi/ -run 'Gate\|Tier\|Reasoning'`;**门禁五条**照抄 `e2e_gate_test.go`(372 行)的结构:deny / ask 批 / ask 拒 / 计划模式拦写 / 取消 fail-closed,**断言目标文件真的不存在** | — |

**pi 特有的泄漏面(比 dsh 多,必须逐条堵)**:`AssistantMessage` 带 `api/provider/model` 三字段;bash 工具注入 `PI_PROVIDER`/`PI_MODEL`/`PI_REASONING_LEVEL`/`PI_SESSION_FILE` 到每条命令(官方文档**还明文教模型去读这些变量**);`get_available_models`/`set_model`/`cycle_model` 会回真实目录(**Go 适配器不实现这三条的转发**);错误体带上游 URL/品牌(复用 `Scrubber`,`SecretsToScrub` 换成 pi 的品牌串)。

**计划模式的实现**:`--tools` 是**启动期**总允许表,rpc 模式下不能逐轮换 —— 所以计划模式只读门**不能**靠 `--tools`,必须靠 `tool_call` 钩子 block。而这恰恰就是门禁通道本身(`Pipeline.Before` 第一段就是 plan mode 只读门),**不是新增成本**。

### 6.3 门禁链路(pi)与 fail-closed 断点

```
pi 的 agent loop
  └─ tool_execution_start(事件,已发给 Go)
  └─ tool_call 钩子(串行、async、可 block)          ← onecreat-gate.ts
        └─ await ctx.ui.input({title:"__onecreat_gate__", …})   ← 官方 dialog,阻塞
              ↓ stdout: {"type":"extension_ui_request","id":…,"method":"input",…}
        [Go] internal/engine/pi 读到 extension_ui_request
              ├─ 解出 toolName + arguments
              ├─ 调 boot.piDecider ─► toolpolicy.Pipeline.Before(ctx, Call{Name,Args,ReadOnly,Preview})
              │     = plan mode 只读门 → 权限门(ask 在此阻塞等真人)→ PreToolUse hook → 写前快照
              └─ 回帧 stdin: {"type":"extension_ui_response","id":…,"value":"{\"decision\":\"deny\",…}"}
        ↑ 扩展拿到 value → decision=="deny" → return { block: true, reason }
  └─ 被 block:工具**不执行**,reason 作为工具结果回给模型
```

| 断点 | pi 的行为 | fail-closed? |
|---|---|---|
| Go 进程死 / 管道断 | dialog 永远等不到响应;stdin 关闭则传输失效抛错 | ✅ 官方保证 "**tool_call errors block the tool (fail-safe)**" |
| Go 明确 deny | `value` 带 `decision:"deny"` | ✅ 扩展 `return {block:true}` |
| 用户取消 dialog | 客户端回 `{"cancelled":true}` → `input` 返回 `undefined` | ✅ **必须显式把 `undefined` 当 deny**(唯一靠纪律的一处) |
| turn 被取消 | `ctx.signal` abort,`await` 被打断抛 `AbortError` | ✅ |
| dialog 超时 | 传 `timeout` 时 pi 自动 resolve `undefined`/`false` | ✅ 建议:**ask 场景不传 timeout**(等真人),纯策略判定传大 timeout(如 60s)兜底 |

唯一的"挂住 ≠ 拒绝"窗口:Go 侧还活着但死锁,扩展无限等。**dsh 有完全相同的性质**,安全上可接受,可用性靠 turn 超时兜底。

### 6.6 分发策略

- **`runtime/node` 共享一份**(pi 要 node ≥22.19,dsh 要 node 20+);发行包里两个 runtime 目录:`runtime/dsh/` + `runtime/pi/`;
- 版本**精确锁死**:`"@earendil-works/pi-coding-agent": "0.84.2"`(无 `^`),`package-lock.json` 入仓。pi 自带 `npm-shrinkwrap.json`(61KB),**上游已经帮我们锁了整棵树**,这比 dsh 的情况更好;
- **不要用 `npx`**(dsh README 已列三条理由:首启下载以分钟计、并发撞 npm cache 权限、preview 会破坏兼容);
- 体积:全打进去 = 90 + 139 + node ≈ **250MB+/平台**。策略:**默认包只带 dsh**,pi 首次切换时**按需下载**(沿用 arduino-cli 一键安装先例);
- **升级门禁**:照抄 dsh README 的「升级必过项」表格写进 `pi/README.md`,并在 CI 上跑;
- Windows:pi **需要 bash**(Git Bash / Cygwin / MSYS2 / WSL),装配期检测 + 可读错误 + 文档;或 Windows 上不提供 pi。

### 6.7 风险 R1–R10 摘要

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | pi 上游改 `tool_call` 契约或 extension UI 子协议 → **门禁静默失效** | 中高 | **致命** | 精确锁版本;升级必过 e2e 门禁五条;扩展里 try/catch 显式 return block(双保险);启动时用 `get_state` 校验协议版本 |

### 6.8 建议:先 spike 对照,再定双养

`docs/dsh调研/00_G0结论.md` §5 当时的判断是"产品 DeepSeek-first + dsh 是模型厂自家 harness"→ dsh 优先级高于 pi,且**没有做 pi 的对照验证**(B 计划从未触发,`05_pi对照验证.md` 从未产出)。

本次调研的新信息:**pi 的协议完备度、文档质量与嵌入友好度明显优于 dsh**;dsh 的优势变成"已经跑通 + 一进程多会话 + 体积小 + 模型厂血统"。

因此建议:

- 如果目标是"**双引擎并存供用户切换**",成本 = 12–17 人日 + 长期双份升级维护;
- 如果目标其实是"**验证 pi 是不是更好的那个 sidecar**",更划算的做法是**先花 P0+P1(5–7 人日)做一个能过门禁 e2e 的 pi spike**,拿它和 dsh 做一次真实对照(生成质量、稳定性、CoT、工具正确率),**再决定要不要长期养两套**。

**并且在投 P1 的 3–4 人日之前**,先花 15 分钟用现成的 `NASApp/brain/node_modules/.bin/pi` 手工验一件事:`ctx.ui.input` 在 `tool_call` handler 里是否**真的**能 await 到 RPC 客户端的 `extension_ui_response`(文档明确写"block until…"且 `ctx.hasUI===true`,但**没有实跑验证**)。

## 9. M0 待拍板的 5 个产品边界问题

> 每问给:**选项 / 推荐 / 理由**。这些是产品边界决策,不是技术难点,**必须先拍板再动代码**——否则很容易做成"OneCreat 里又造一个 project_sync"。

### 问题 1 · 发号权威放哪? ✅ 已拍板 2026-08-23 → 见 [`01_M0决策记录.md` §1.1](01_M0决策记录.md)

| 选项 | 说明 |
|---|---|
| A | 迁移期保留 NAS 权威(`internal/numbering` 出一个 HTTP 适配)→ **冻结日一次性切本地文件** |
| B | 一步到位切本地(`课题/.onecreat/project_codes.json`) |

**推荐:A。**
理由:发号是"唯一权威"型数据,**双写必冲突**;A 让 M1–M4 期间 NASApp 与 OneCreat 可以并行使用而不打架,把切换风险压缩到 M5 的一天。B 的风险是并行期两边各发一个号,后果不可逆(项目编号是三端身份证)。A 的额外成本很小:`Issuer` 接口本来就要写,NAS 实现只是多一个 HTTP 客户端 + 现成的 `expected_code` 回验。

### 问题 2 · NAS 项目总库 / 学生软链 / SMB 共享继续维护吗? ✅ 已拍板 2026-08-23 → 见 [`01_M0决策记录.md` §1.2](01_M0决策记录.md)

| 选项 | 说明 |
|---|---|
| A | 继续由外部 `project_sync.py` 维护,OneCreat 只提供一个"运行同步"按钮(调外部脚本) |
| B | 完全退役,只留 Mac 单点 |

**推荐:A。**
理由:学生视角(NAS `2026上课/<真名>/项目文件/` 软链)、老师用 SMB 看文件、上课照片落点**三件事都依赖 NAS 总库**,退役会直接影响正在上的课。而 `project_sync.py` 是**已经跑通、与 OneCreat 正交**的外部脚本——把它保留成"外部工具 + 一个按钮"是成本最低的解耦。同时明确:OneCreat **不重写 rsync 编排**,只吸收其"分类投放"的业务规则进 `bucket.Classify`。

### 问题 3 · 教师平台项目包上传由谁做? ✅ 已拍板 2026-08-23 → 见 [`01_M0决策记录.md` §1.3](01_M0决策记录.md)

| 选项 | 说明 |
|---|---|
| A | 继续只走 iOS(写 token 只在 Keychain,NAS 后端绝不持有) |
| B | 让 OneCreat 持老师 token 直传 |

**推荐:A(至少 M0–M5 期间)。**
理由:"写凭证只在 iOS Keychain"是 NASApp 已经立下的安全边界,而 OneCreat 现在**只持自己的网关 token**(`account.Gateway`,`boundary_test.go` 全树扫描守着它)。选 B 意味着 OneCreat 要多持一类高权限凭证、多一套平台写 API 的错误处理,而收益只是"少切一次 App"。留到线 C 商业化时,与"老师级授权模型"一起重新评估。

### 问题 4 · NASApp 并行期多长?哪些功能继续用 NASApp? ✅ 已拍板 2026-08-23 → 见 [`01_M0决策记录.md` §1.4](01_M0决策记录.md)

| 选项 | 说明 |
|---|---|
| A | 并行到 M5(约 3–5 个月),期间看板 P 卡 / C 卡教务 / 照片上传 / 平台上传全部继续用 NASApp |
| B | M3 后即停用 NASApp 的科创工作流入口,只留教务与文件站 |

**推荐:A,但把边界写死。**
理由:M4 之前 OneCreat 没有 UI,老板在手机上没有替代品;而 P 卡 stage 在 M5 之前仍是权威(§4.1)。建议在 M0 的决策记录里写死一张表:**哪些入口在哪一期停用**。同时明确 **C/B 卡教务档案永久留在 NASApp**(§4.11 不迁清单),这样"并行"只针对科创工作流那部分,不是整个 NASApp。

### 问题 5 · pi 引擎:直接双养还是先 spike 对照? ✅ 已拍板 2026-08-23 → 见 [`01_M0决策记录.md` §1.5](01_M0决策记录.md)

| 选项 | 说明 |
|---|---|
| A | 直接双养(P0–P5 全做,12–17.5 人日 + 长期双份升级维护) |
| B | 先做 P0+P1(5–7 人日)拿能过门禁 e2e 的 spike,与 dsh 真实对照后再定 |

**推荐:B。**
理由:00_G0 当时选 dsh 时**没有做 pi 的对照验证**,现在的新信息(pi 协议完备度与文档质量明显更好)只够支撑"值得一试",不够支撑"值得长期双养"。B 的成本只有 A 的四成,而且 P0+P1 的产出在 A 路线下**一行都不浪费**。另外 R10(双养的长期维护成本)是**确定发生**的,不该在没有对照数据时就先承担。
**并且在投 P1 之前**,先做那个 15 分钟的手工验证(§6.8)。
