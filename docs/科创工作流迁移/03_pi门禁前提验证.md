# pi 门禁前提验证(实跑)

验证日期:2026-08-23
验证人:Claude(验证工程师角色)
被验证的假设(来自 `调研/03_双引擎可行性_pi_vs_dsh.md` §3.3–§3.4、§4.2):

> pi 在 `--mode rpc` 下,扩展的 `tool_call` 钩子里 `await ctx.ui.input(...)` 能真的**阻塞**等 RPC 客户端从 stdin 回的 `extension_ui_response`;回 deny 时工具**不执行**;不回帧 / 回 `cancelled` 时工具也**不执行**(fail-closed)。

## 结论:**成立**(5/5 用例通过),但**多出一条必须处理的实现约束**(见 §6「新发现」)。

`tool_call` 钩子 + extension UI 子协议构成的门禁通道,在真机上按文档承诺的语义工作:阻塞是真的、deny 是真的不执行、无响应与 cancelled 都 fail-closed。pi 可以合法声明 `CapGatedTools`。
**新增约束**:`abort` 命令**不会**解除一条已挂起的 `extension_ui_request`——turn 会永久挂住(文件仍然安全)。Go 适配器的 `TurnHandle.Cancel` 必须**先对所有未决门禁请求回一帧 deny/cancelled**,再发 `abort`,否则 `Wait()` 永不返回。

## 2. 启动命令(实际用的 flag,逐字)

```
pi --mode rpc \
   --session-dir <probe>/sessions \
   --tools read,write,edit,bash,grep,find,ls \
   --no-extensions -e <probe>/gate.ts \
   --no-skills --no-context-files -na \
   --provider deepseek --model deepseek-v4-flash --thinking minimal
```

env(白名单,照 NASApp `buildPiEnv` 的纪律):`PATH/HOME/USER/SHELL/LANG/TMPDIR` + `TERM=dumb` + `DEEPSEEK_API_KEY` + `PI_CODING_AGENT_DIR` + `PI_CODING_AGENT_SESSION_DIR` + `PI_OFFLINE=1` + `PI_TELEMETRY=0`。

**`--no-extensions` 不会关掉 `-e` 显式加载的扩展**——实测 `gate.ts` 正常加载(stderr 有 `[gate] extension loaded`),与文档 `usage.md:235` 一致,不需要去掉该 flag。

扩展形态必须是 `export default function (pi) { pi.on('tool_call', async (event, ctx) => …) }`(照 NASApp `ops-template/guard.ts`);顶层裸调 `pi.on(...)` 不是本版的加载形态。

`ctx.mode === "rpc"`、`ctx.hasUI === true` 实测为真(钩子里打到 stderr 的日志证实)。

### 阻塞的时间证据(U1,单位=从 spawn 起的秒)

```
1.888  << tool_execution_start  tool=write
1.889  << extension_ui_request  method=input title=__onecreat_gate__
2.395  >> extension_ui_response value=deny      ← 我方故意压了 506ms 才回
2.396  << tool_execution_end    isError=true "onecreat gate: denied (test)"
```

`tool_execution_end` 出现在我方回帧后 **1ms**,而请求已发出 **506ms**:说明 pi 侧确实**阻塞在 `ctx.ui.input` 上等 stdin**,不是超时兜底、也不是先执行后回填。U2/U3b 的形状完全相同(0.5s 压测 → 回帧后 1~3ms 出结果)。

## 4. 帧样例(脱敏)

门禁请求(原始 JSON,只删了无关字段):

```json
{"type":"extension_ui_request",
 "id":"6a06760e-2406-41a5-b9ea-f536d172ae86",
 "method":"input",
 "title":"__onecreat_gate__",
 "placeholder":"{\"tool\":\"write\",\"args\":{\"path\":\"probe_1.txt\",\"content\":\"hello\"},\"toolCallId\":\"call_00_ET_Ks7…\"}"}
```

即:**扩展传给 `ctx.ui.input(title, placeholder)` 的第二个参数原样出现在 `placeholder` 字段里**,可以直接当载荷通道用(Go 侧解析 `placeholder` 得到 `{tool,args,toolCallId}`)。`title` 作为哨兵串工作正常。

回帧(客户端 → stdin):

```json
{"type":"extension_ui_response","id":"6a06760e-…","value":"{\"decision\":\"deny\",\"reason\":\"test\"}"}
{"type":"extension_ui_response","id":"2a5574e3-…","cancelled":true}
```

被拦后的工具结果(pi → stdout):

```json
{"type":"tool_execution_end","toolCallId":"call_00_…","toolName":"write",
 "result":{"content":[{"type":"text","text":"onecreat gate: denied (test)"}],"details":{}},
 "isError":true}
```

一轮完整的帧类型序列(U1):
`response → agent_start → turn_start → message_start → message_end → message_start → message_update ×20 → message_end → tool_execution_start → extension_ui_request → tool_execution_end → message_start → message_end → turn_end → turn_start → message_start → message_update ×3 → message_end → turn_end → agent_end → agent_settled`

注意:**`tool_execution_start` 在门禁请求之前发出**(带 `toolName` + 完整 `args`)。也就是说前端会先看到"要调 write",再看到裁决结果——与 dsh 一致,mapper 侧要保证被 deny 的调用有一条对应的 `ToolResult`,不能只发 `ToolDispatch`。

## 5. 钩子触发面

| 工具 | 是否触发 `tool_call` | 证据 |
|---|---|---|
| `write` | ✅ | U1/U2/U3/U3b |
| `edit` | ✅ | U4(deny 后 `probe_2.txt` 内容未变) |
| `bash` | ✅ | U4(deny 后 `probe_bash.txt` 未生成) |
| `ls` / `read` | ✅ 触发,但走放行分支 | U4 stderr 有 `allow-passthrough tool=ls/read`,工具正常执行 |

结论:**钩子对所有内建工具一致触发**,是否门禁完全由扩展自己判,与 OneCreat 把 `ReadOnly` 判断放在 Go 侧(`toolpolicy.Pipeline.Before`)的设计吻合——扩展应当**对所有工具**都发门禁请求,由 Go 决定放行,而不是在扩展里硬编码工具白名单(本次验证为了做对照才在扩展里分了叉)。

## 6. 新发现(会改变 P1 设计的两条)

### 6.1 ⚠️ `abort` 解不开挂起的门禁 dialog(U5)

发送 `{"type":"abort"}` 后:

- pi **没有**回 `response`(连 `command:"abort"` 的失败响应都没有);
- **没有**任何后续事件(无 `agent_end`、无 `agent_settled`);
- 扩展的 `ctx.ui.input` **没有**抛 `AbortError`,stderr 里没有 `gate-error`;
- 我方等到 120s 超时才放弃,`probe_5.txt` 始终不存在(安全性 OK)。

调研文档 §4.2 里"turn 被取消 → `ctx.signal` abort → handler 里 `await` 被打断抛 `AbortError`"这条**未被实测证实**——至少 `ctx.ui.input()` 这个 await 不吃 turn 的 abort。

**对 P1 的影响(必须落进适配器设计)**:

1. `piTurnHandle.Cancel()` 的顺序必须是:**先对所有未决的门禁请求回 `{"cancelled":true}`(或 `{"decision":"deny"}`)→ 再发 `abort`**。Go 侧因此必须维护一张"未决 `extension_ui_request` id → 是否已回"的表(和 dsh 的 pending map 同形)。
2. 稳妥起见 `Cancel` 还要带**兜底 kill**:发完 abort 后等一个短超时(dsh 用的是 6s 量级),没等到 `agent_settled` 就杀进程组。
3. 保险起见,门禁 dialog 应当**传 `timeout`**(如 60s)。文档说超时会自动 resolve 为 `undefined`,而 `undefined` 在我们的扩展里已经是 deny(U3b 已实测 `undefined` 路径),所以传 timeout 只会让挂死变成"拒绝并收敛",不会削弱安全性。**建议:交互式审批(等真人)也传一个大 timeout,而不是不传。**

### 6.2 关闭 stdin 不会让扩展抛错(U3)

关掉 pi 的 stdin 后,挂起的 `ctx.ui.input` **没有**抛错,钩子继续挂着。调研文档 §4.2 第一行写的"若 stdin 关闭,pi 侧 dialog 会因传输失效抛错 → 官方保证 fail-safe"**不成立**——实际行为是"永远挂着"。

安全结论不变(挂住 ≠ 放行,文件确实没被写),但**可用性结论要改**:Go 进程死掉时,pi 子进程不会自己收敛,只会变成一个挂住的孤儿。因此 pi 适配器必须保证子进程与 Go 进程**同生共死**(在 `runtime` 的 session scope 上注册 kill;桌面端关标签页时确实会走到)。

## 7. SaaS 脱敏风险(R5)证据

事件流里**出现真实厂商名/模型名的确切字段**(不含 key):

| 帧类型 | 字段路径 | 实测值 |
|---|---|---|
| `message_start` | `.message.api` / `.message.provider` / `.message.model` | `openai-completions` / `deepseek` / `deepseek-v4-flash` |
| `message_end` | 同上 | 同上 |
| `turn_end` | 同上 | 同上 |
| `agent_end` | `.messages[].api/provider/model`(整段历史) | 同上 |
| `turn_end` | `.message.content[].thinkingSignature` | `reasoning_content`(DeepSeek 特有,弱信号) |

三个字段名固定为 `api` / `provider` / `model`,**mapper 不透传这三个字段即可**;但注意 `agent_end` 会把**整段消息历史**吐出来,里面每条 assistant 消息都带这三个字段——脱敏必须**递归**,不能只处理顶层。这比 dsh 面更大。缓解方案与调研文档 §3.6 一致:provider 名固定成 `onecreat-gateway`、model id 固定成 `tier-N`(即在我们自己下发的 `models.json` 里就用假名),这样这些字段天然就是假名,`scrub.Scrubber` 只做兜底。

## 9. 遗留问题(未验证)

1. **并发工具的门禁顺序**:文档说同一条 assistant 消息的兄弟工具调用"preflight 串行、执行并发"。本次模型每轮只发一个工具调用,**未实测**多工具并发时门禁请求是否真的串行到达。Go 侧的 pending map 无论如何要能处理多条未决请求。
2. **`timeout` 字段的实际行为**:本次没给 dialog 传 `timeout`,超时自动 resolve 为 `undefined` 这条只有文档、没有实测。
3. **`extension_error` 帧**:扩展抛异常时应发 `extension_error`;本次扩展全程 try/catch 未抛,**未观察到该帧**。"handler 抛错 = 工具被拦"这条官方保证仍是文档级,没有实测(我们不依赖它——扩展显式 catch 并 return block)。
4. **`--tools` 与桥接工具**:本次没注册自定义工具,NASApp 踩的"允许表少写业务工具名 → 被一起关掉"的坑**未复现验证**。`complete_step` 桥接落地时必须复测。
5. **resume / 多轮**:每个用例都是新进程单轮,`switch_session` / `--session-id` resume 未测。
6. **Go 侧真实实现**:本次用 Python 手工模拟 stdin/stdout,**没有**跑真的 `internal/engine/pi`(还不存在)。JSONL 分帧、16MB 上限、pending map 这些 Go 细节仍需在适配器落地时单测。
