## 2. 总体裁决

这轮重构有不少正确方向，尤其是：

- Event wire 收口；
- Web RPC 显式 allowlist；
- 显式 Workspace Context；
- TabManager 单一状态真源；
- Runtime Scope 骨架；
- Runtime Factory 与 Workspace 资源共享；
- Desktop App / Controller 的服务化拆分；
- Native Agent 内的 tool policy 提取；
- Gateway 对象化；
- Event durable / ephemeral 分类；
- Session metadata registry；
- 小型 `TurnEngine` 接口。

但是，最终集成在 **dsh 与 OneCreat 产品策略、Session 真源、能力矩阵、取消生命周期** 四个关键交界处断裂。当前状态不是“最后只有小修”，而是存在会导致：

- 未经 OneCreat Permission/Plan/Hook/Checkpoint/Evidence 门禁执行写操作；
- UI 显示 rewind/fork/new/resume 成功，但 dsh 实际上下文没有变化；
- dsh 会话不正确落盘、历史为空或错标 native；
- 用户取消一次后整个 dsh 会话永久失效；
- 慢 SSE 客户端丢失 durable 状态后无法真正恢复；
- 多 workspace `.env` 相互污染；
- Workspace 关闭/重开竞态复用已关闭服务。

因此：

> **在以下 P0/P1 finding 修复、补齐测试并取得完整 CI 前，不得合并 #2–#14。**

# 4. 详细 Findings

## AR-R01 — P0：dsh 工具执行绕过 OneCreat tool policy

### 源码证据

- `internal/toolpolicy/policy.go` 承载 plan-mode writer block、Permission gate、Pre/PostToolUse、checkpoint pre-edit、Evidence、Jobs、Memory。
- Native `agent.Agent` 在自己的 `t.Execute(...)` 前后调用 `Pipeline.Before/After`。
- `internal/engine/dsh/adapter.go` 明确写出：dsh 的工具运行在自己的进程中，OneCreat 权限门够不着。
- `control.Controller.runEngineTurn` 只执行 `engine.Start(...).Wait(...)`，没有任何 tool-call interception。
- `internal/engine/dsh/mapper.go` 只把 dsh 已经发生的 `tool/call`、`tool/result` 映射为显示事件，此时写入或 shell 已经执行完毕。

### 影响

在 `engine="dsh"` 下，下列产品安全与诚实性能力不成立：

- Permission allow/ask/deny；
- 交互式 writer approval；
- plan mode 只读门；
- PreToolUse 阻断 hook；
- writer 执行前 checkpoint；
- Evidence / `complete_step` 真实性；
- Jobs / Memory 的 call-context 注入；
- Desktop 串口抢占前释放回调。

这是安全与产品语义问题，不是单纯“能力少一点”。`AGENTS.md` 当前声称这些策略位于 Engine seam 之上、对两种引擎一视同仁，与实际源码相反。

### 必须修复

二选一，默认采用 fail-closed：

1. **推荐：在 dsh 协议不能把 tool call 委托给 OneCreat 执行前，禁止 dsh 使用 writer/shell/tool execution。** 启用 dsh 时若无法证明只读，装配失败并给出明确错误；或将 dsh 限制为纯模型/流式引擎，工具全部由 OneCreat host 执行。
2. 若 dsh 协议支持 hosted/delegated tools，则建立 tool-call bridge：dsh 只能提出调用，OneCreat 依次执行 `toolpolicy.Before → Tool.Execute → toolpolicy.After` 后把结果回传 dsh。

不得仅在 dsh 发出 `tool/call` 事件后做事后检查。

### 验收测试

- dsh 下 deny writer：文件没有变化，模型收到 blocked result；
- dsh plan mode：writer/shell 不可执行；
- dsh writer：checkpoint 在变更前生成；
- dsh tool receipt：Evidence 可验证，失败调用不能成为成功证据；
- PreToolUse hook 可阻断 dsh call；
- 测试必须使用可观测的假 sidecar，不接受只测 capability 常量。

## AR-R02 — P0：Capability 只声明、不执行

### 源码证据

- `internal/engine` 定义 `CapApproval`、`CapResume`、`CapFork`；dsh 只声明 `CapStreaming`。
- `internal/control/branches.go` 的 `Fork`、`Branch`、`SwitchBranch` 直接读写 `c.executor.Session()`，没有查询 `c.engine.Supports(...)`。
- `Controller.NewSession`、`Rewind`、`Compact`、`Summarize*` 同样直接重写 native executor session。
- HTTP server 无条件暴露 `/approve`、`/new`、`/rewind`、`/fork`、`/resume`、`/branches` 等端点。
- PR #14 自己也承认“能力矩阵尚未在每个前端逐条执行”。

### 影响

在 dsh 模式下：

- native 影子 Session 可能被 rewind/fork/new/resume；
- dsh sidecar 仍保持原会话；
- 前端收到成功返回或 notice，但下一轮 dsh 上下文没有变化；
- `/new` 可能只换 OneCreat metadata/file，sidecar 仍是 `DefaultSessionID`；
- Approval API 存在但 dsh 工具不等待它。

### 必须修复

- Controller 提供稳定的 `Capabilities()` / `Supports()` 只读入口；
- 每个依赖能力的原语必须在任何状态修改之前 fail-closed；
- unsupported 返回 typed error，例如 `ErrUnsupportedCapability{Engine, Capability, Operation}`；
- HTTP 使用明确的 409/422，Desktop/CLI 显示不可用原因；
- UI 根据 capability 隐藏或禁用入口，但后端仍必须独立校验；
- 不得把 Resume/Fork 等方法塞回 `TurnEngine`，可使用独立的 session backend/capability service。

### 验收测试

覆盖 dsh 下：Approve、Plan execution、Compact、NewSession、Rewind、Fork、Branch、SwitchBranch、Resume、Summarize。所有 unsupported 操作都必须：

- 返回明确错误；
- 不修改 native Session；
- 不修改 checkpoint；
- 不修改 session metadata；
- 不向 sidecar发送伪操作。

## AR-R03 — P0：dsh Session / Persistence 仍硬编码 native

### 源码证据

- `internal/session` 只有 `EngineNative` 常量。
- `control.newSessionStore(...)` 只接收 `*agent.Agent`，注册时固定 `session.EngineNative`。
- `sessionStore.Save/History/MessageCount` 全部读取 native executor 的 `agent.Session`。
- dsh adapter 只把事件输出到 Sink，不把消息追加到 native Session；dsh 真实 transcript 在 sidecar。
- `Controller.runTurnWithRaw` 的 autosave、plan proposal、Stop hook、checkpoint boundary 都读取 `c.session.History()/MessageCount()`。

### 影响

- dsh 记录会被错误标记为 native；
- dsh 一轮前后 native MessageCount 不变，autosave/touch 逻辑失真；
- `/history`、Desktop history、plan approval proposal 为空或陈旧；
- Stop hook 拿不到 dsh 最终回答；
- Session title/preview/turn count 与实际 dsh 对话不一致；
- “一个 Session 只有一个 transcript 真源”的 Plan 11 目标没有实现。

### 必须修复

- Session metadata 注册必须接收真实 `engine name + opaque store reference + stable session id`；
- 为 native 与 dsh 定义独立 transcript backend，不要从 `*agent.Agent` 猜；
- dsh 若当前协议没有可读取/持久化的 transcript：
  - 明确声明不支持 history/resume/fork；
  - 不创建伪 native transcript；
  - UI 标记 ephemeral session；
  - 重启/切换前给出数据不可恢复提示；
- 若 dsh 提供 store，则由 dsh backend 独占解析，Registry 只保存 opaque ref；
- `Controller.History`、autosave、plan proposal、Stop hook 必须通过 session backend，或在 unsupported 时禁用相应功能。

### 验收测试

- dsh Session Record 的 Engine 为 `dsh`；
- Store 是真实 dsh opaque reference，而不是空 native JSONL；
- dsh history 可用时能恢复；不可用时所有相关入口 fail-closed；
- 新建、重建、关闭、重启后 metadata 与 sidecar 会话一致；
- 不允许 native+dsh 双写 transcript。

## AR-R04 — P0：取消一轮后 dsh sidecar 永久失效

### 源码证据

- `dsh.turn.Cancel()` 调用 `inner.Cancel()`；
- `dsh.Engine.Cancel()` 直接 `Kill()` 子进程；
- `dsh.Engine.Start()` 只允许执行一次，`started` 后无法再次 Boot；
- Adapter 在下一轮只会继续对原 `rpc` 调用 `Submit`，没有重启/重新 initialize 路径；
- 现有测试只验证当前 turn 被取消，没有验证“取消后再发下一轮”。

### 影响

用户点一次 Cancel 后，该 tab/controller 仍显示存在，但 dsh 进程已死；后续消息会落到失效 RPC，直到整个 controller 被重建。

### 必须修复

- Adapter 必须有明确生命周期状态：ready/running/dead/restarting/closed；
- mid-turn cancel 若只能杀进程，则 cancel 完成后自动重建并 initialize 一个新 sidecar；
- 如果无法保留会话，必须把 Session 标记为 terminal/ephemeral 并要求显式重建，不能继续显示 ready；
- sidecar 意外退出同样走统一恢复或 terminal 路径；
- 严禁下一轮写入旧 `LineClient`。

### 验收测试

- start → cancel → next start 可以成功；
- cancel 与 turn/end 竞争无 double-close/deadlock；
- sidecar crash → 明确事件 + 下一轮恢复/拒绝；
- `go test -race` 与 goleak 覆盖。

## AR-R05 — P1：dsh 模式仍完整装配未使用的 native runtime

### 源码证据

`boot.Build` 在 `selectEngine` 之前无条件完成：

- 解析 native model/provider；
- API key 校验与 Provider 创建；
- Tool Registry、MCP Host、Task/Skill/Memory tools；
- native `agent.Agent` / optional Coordinator；
- Jobs、Hooks、Permission、Balance client；

最后才选择 native 或 dsh。dsh 模式仍把这个 native executor 塞进 Controller 作为影子。

### 影响

- dsh 仍依赖一个本不该使用的 native provider/model 配置；
- `RequireKey=true` 可能因 native key 缺失拒绝启动，尽管 dsh 只需要 gateway token；
- MCP / tools / jobs 可能重复启动，与 dsh 自己的 tool runtime 冲突；
- 启动慢、资源浪费、边界不清；
- 正是 AR-R01/AR-R03 中“native 影子状态”的来源。

### 必须修复

把 Boot 分为：

- Engine-independent application/runtime assembly；
- NativeEngine assembly；
- DshEngine assembly；

只构造当前引擎实际需要的依赖。若某个 Application service 对 dsh 不支持，显式 capability/fail-closed，不要靠构造一个 unused native Agent 冒充。

## AR-R06 — P1：dsh token 生命周期与子进程秘密边界不正确

### 源码证据

- dsh 在 Boot 时只读取一次 `Gateway.Token()`；
- running sidecar 不会在 Gateway refresh 后更新 token；
- `childEnv()` 从 `os.Environ()` 开始，再追加 dsh 变量。

### 影响

- 长时间运行的 dsh 会话在 access token 过期后失败；
- dsh 子进程继承进程内全部秘密，包括其他 Provider key、项目 `.env`、CI/宿主变量；
- 与 Plan 09 的“CredentialSource 每次请求动态读取”目标不一致。

### 必须修复

- 子进程环境改为 allowlist；
- Token 通过受控 RPC/credential channel 动态提供，或在 refresh 后安全滚动重启 sidecar；
- 记录 token generation，禁止把旧 token 继续用于新请求；
- 增加“其他 provider secret 不进入 dsh env”的测试。

## AR-R07 — P1：Event Protocol V2 没有真正恢复 durable 状态

### 源码证据

- `eventstream.Hub` 在 durable overflow 时把 subscriber 标记 overflow；
- SSE handler 发一个命名事件 `stream_reset` 后断开；
- Frontend `EventSource` 只使用 `onmessage`，没有注册 `stream_reset` listener；
- 自动重连后没有读取 `/history`/Meta/PendingApprovals/PendingAsks/Running snapshot；
- Frontend 不检查 `sequence` gap；
- HTTP `/history` 只返回 transcript，不含 pending prompts、running、latest sequence。

### 影响

慢客户端一旦错过 ApprovalRequest、AskRequest、ToolResult、Message 或 TurnDone：

- 重新连接后仍然不知道丢了什么；
- 审批可能永远不可见；
- UI 可能一直显示 running；
- tool card / final message 缺失；
- V2 envelope 只能“发现理论上的 gap”，实际客户端没有使用。

### 必须修复

至少提供一个权威 snapshot：

- transcript/history；
- running/turn state；
- pending approvals；
- pending asks；
- current session/tab/stream incarnation；
- latest durable sequence。

Frontend 必须在：

- `stream_reset`；
- reconnect `onopen`；
- sequence gap；

任一发生时执行 resync。可进一步实现 Last-Event-ID replay，但不能只自动重连同一空流。

### 验收测试

强制 subscriber overflow，验证客户端最终恢复到正确 transcript、running=false、pending prompt 可见，且不会重复消息。

## AR-R08 — P1：Event identity 与 dsh event mapping 不完整

### 8.1 Desktop `sessionId` 永远为空

- `eventwire.Stamper` 支持 `sessionID`；
- Desktop `newEventSink` 固定 `NewStamper("", tabID)`；
- 同一个 sink 跨 `/new`、resume、controller rebuild 使用，sequence 是 tab 流而不是 session 流。

结果：V2 `sessionId` 字段不能用于关联会话，客户端无法区分 session switch 与普通连续事件。

### 8.2 dsh ToolResult 无关联字段

`dsh.mapper` 的 ToolDispatch 带 ID/Name，但 ToolResult 只填 Output/Err，没有 ID/Name。现有测试也没有要求 correlation。前端无法可靠把结果归并到对应 tool card。

### 8.3 dsh 丢弃未映射的 durable 事件

`mapper.go` 默认丢弃 `todo/write`、step、compaction 等 dsh 事件。它们不是“可随便丢的文本 delta”，但没有 capability、warning 或 snapshot 替代。

### 必须修复

- Envelope 使用实际 stable session ID，并增加 stream incarnation；
- session change 时明确重置/换 incarnation，而不是悄悄沿用；
- dsh tool result 必须携带 call ID、name、parent/correlation；
- 对每个 dsh event type 明确：映射、持久化、降级 notice 或明确 unsupported；不得静默丢弃状态型事件。

## AR-R09 — P1：Session Registry 多 owner / 多进程 lost update

### 源码证据

- `Registry.mu` 只保护单个 Registry 实例；
- 每次操作虽然先重读磁盘，但仍是 read-modify-write 整份 `.sessions.json`；
- Desktop sessionService 与每个 Controller 各自 `session.Open(dir)`；
- 两个 owner 可同时读相同旧版本，各自写回，后写者覆盖前写者；
- `session.go` 注释已承认该窗口，但测试只覆盖同一个 Registry 实例的 goroutine，没有覆盖两个 Registry owner。

### 影响

并发 tab、Desktop+CLI、两个进程同时更新 title/display/touch/record 时，Session metadata 可能丢失。

### 必须修复

- 进程内由 RuntimeFactory/ProcessRuntime 共享一个 Registry；
- 跨进程使用文件锁、append journal 或带版本 CAS 的事务式更新；
- 测试必须创建两个独立 Registry 实例；至少一个测试使用两个进程或可控 barrier 复现交错。

## AR-R10 — P1：Workspace `.env` 仍污染进程全局状态

### 源码证据

- `config.LoadIn(ws)` 调用 `loadDotEnvIn(ws)`；
- `loadDotEnvFile` 用 `os.Setenv`，且已有值不覆盖；
- 多个 Workspace 同进程时，第一个加载的同名 key 永久获胜。

### 影响

Workspace A `.env`：`API_KEY=A`，Workspace B `.env`：`API_KEY=B`，则 B 的 Provider/Plugin 可能继续拿 A。并发 tab 不具备秘密隔离；dsh 又会通过 `os.Environ()` 继承全部值。

### 必须修复

- `.env` 解析为 Workspace-local immutable overlay；
- process env 仍可作为最高优先级显式 override，但不得被项目文件修改；
- Provider credentials、Plugin env expansion、tool subprocess env 接收显式 overlay；
- 多 workspace 同名变量隔离测试。

## AR-R11 — P1：Factory 双注册表竞态与配置代际问题

### 源码证据

- `runtime.Process` 自己维护 workspace scope/refcount；
- `boot.Factory` 另有 `services map[root]*workspaceServices`；
- `OpenWorkspace` 先进入 Process registry，再进入 Factory registry；
- 最后一个 `Release` 先关闭 scope，之后才删除 services；
- 并发 reopen 可创建新 scope，却从 Factory map 取到旧 scope 上的已关闭 services；
- `WorkspaceSpec` 只在第一次 open 时使用。

### 影响

- last release 与 reopen 竞争时，新 Session 可能复用已关闭 LSP manager；
- services entry 可能被迟到的 delete 删除；
- Settings rebuild 使用 Hold 保持 Workspace 不关闭，LSP/CodeGraph 配置变化可能一直不应用，直到全部 holder 消失。

### 必须修复

- scope、services、refcount 合并为一个受同一锁控制的 authoritative Workspace entry；
- Release/reopen 使用 generation 或原子状态；
- WorkspaceSpec 有 fingerprint/generation，配置变化时安全 reconfigure/replace，或明确拒绝 live apply；
- 增加“最后释放与重开并发”race test，以及 live config change test。

## AR-R12 — P1：TurnRuntime 未接入真实 turn

### 源码证据

- `runtime.Session.BeginTurn()` / `runtime.Turn` 已实现；
- `control.turnState.Guarded` 仍从 `context.Background()` 创建 context；
- Controller 不持有 runtime Session，也不调用 BeginTurn/End/Cancel；
- per-turn evidence/tool batch/usage 没有注册到 Runtime Turn scope。

### 影响
